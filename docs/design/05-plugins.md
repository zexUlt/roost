# 5. Плагины

Плагин — каталог:

```
plugins/claude/
  plugin.json
  qml/            # UI: панели, страницы настроек (необязательно)
  backend/        # любой исполняемый файл с JSON-RPC по stdio (необязательно)
  lib/            # нативная библиотека на SDK (необязательно)
```

`plugin.json`:

```json
{
  "id": "claude",
  "version": "0.1.0",
  "api": "0",
  "backend": { "command": ["backend/claude-adapter"] },
  "contributes": {
    "agents": [{ "id": "claude", "capabilities": ["backgroundDaemon", "nativeTuiAttach"] }],
    "panels": [{ "id": "transcript", "qml": "qml/Transcript.qml",
                 "inputs": { "session": "SessionRef" }, "outputs": {} }],
    "commands": [{ "id": "claude.newSession", "title": "New Claude session" },
                 { "id": "claude.stop", "title": "Stop Claude session" },
                 { "id": "claude.remove", "title": "Remove Claude session" },
                 { "id": "claude.respawn", "title": "Respawn Claude session" },
                 { "id": "claude.respawnAll", "title": "Respawn all Claude sessions" }],
    "keybindings": [{ "command": "claude.newSession", "key": "Ctrl+Alt+N", "mac": "Cmd+Alt+N" }],
    "settings": "qml/Settings.qml"
  }
}
```

| Часть | Как работает | Где выполняется |
|---|---|---|
| UI | QML с диска через `QQmlComponent`, без шага компиляции; в режиме разработки перезагружается при изменении файла | GUI-поток окна, рендер — поток рендера |
| API для QML | один QML-синглтон `Roost` (модуль `Roost.Api`) со свойствами `commands`, `store`, `bus`, `connected` и методами `call` и `bindingKey`; `TerminalItem` — зарегистрированный QML-тип: свойство `session` (`SessionRef` или `null`) показывает сессию через тёплые терминалы окна (`api::Api::Terminals()`): тёплая сессия показывается сразу, остальные открываются через `session.open`; смена сессии или `null` канал не закрывает, `status` (`none`, `opening`, `open`, `ended`, `failed`, `disconnected`) и `statusMessage` говорят, как идут дела, `reopen()` открывает кончившуюся, отказавшую или потерянную сессию заново | GUI-поток |
| Лёгкая логика | JavaScript в QML | GUI-поток |
| Тяжёлая логика и состояние | бэкенд-процесс плагина, любой язык | отдельный процесс, запускает `roostd` |
| Нативный код | библиотека на SDK с C ABI; свои QML-типы на C++ — QML-модуль плагина (ниже) | GUI-поток окна и потоки самого плагина |

- Встроенные фичи живут в `plugins/` и ходят через тот же API: список сессий с категориями, пинами, архивом и непрочитанными; терминальная панель; команды самого окна (плагин `shell`: манифест без панелей и бэкенда, §16); уведомления; PR по worktree; keep-awake; адаптер Claude. Заменить фичу — выключить встроенный плагин и поставить другой с теми же вкладами. Выключает ключ `plugins.disabled` документа `settings` (08-state.md): список id плагинов, например `{"plugins": {"disabled": ["sessions"]}}`. `roostd` пропускает при загрузке плагины с этими id, встроенные и пользователя, и это не проблема: id пропущенных установленных плагинов (по одному, в порядке загрузки) `roostd` отдаёт в `disabled` ответа `plugins.list`, и окно называет такой плагин в заглушке его панели (06-panels.md); id, которого нет среди установленных, ничего не делает. Список читается один раз при старте `roostd` (перечитывания плагинов в демоне нет), поэтому правка действует после его перезапуска. Значение, которое не массив строк (или `plugins`, который не объект, или нечитаемый `settings.json`), — проблема в `problems` ответа `plugins.list` и в логе `roostd`, и ничего не выключено. Окно выбирает список и терминал раскладки по умолчанию по их портам (06-panels.md), так что замена списка — каталог плагина с панелью, у которой выход `selected` типа `SessionRef`, плюс этот ключ, без правок кода. Переключателя в окне настроек нет.
- Конфликт вкладов (две команды с одним id, два хоткея на одну клавишу) решается порядком загрузки плюс явным переопределением пользователя в `keymap.json` (§16); конфликт виден в палитре команд (§16, «Палитра»).
- API версии `0` нестабилен до SDK 1.0 (критерий — в «Версии SDK» ниже).
- Разовый вызов из QML (`Roost.call`, `commands.run`, `commands.registerCommand`, `store.get`, `store.set` и `store.patch`, `keymap.get`, `keymap.setCommand`, `keymap.resetCommand`, `bus.publish`, `sessions.refresh`) принадлежит панели, в чьём QML-контексте определена вызывающая функция; помощник на JS, определённый в оболочке или в файле `.pragma library`, принадлежит окну. Окно регистрирует контекст каждой панели при её создании (`PluginLoader`, `src/roost/plugin_loader.hpp`). После выгрузки колбэки вызовов панели не вызываются независимо от порядка выгрузки, а вызов из выгружаемой панели отбрасывается и в `roostd` не уходит. Сигналы так не обрываются: при выгрузке отключаются `Connections` и `Roost.store.changed.connect(объект, функция)`, а `Roost.store.changed.connect(функция)` живёт до явного `disconnect`. Вызов знает и плагин, чей код его делает, и `keymap.setCommand` и `keymap.resetCommand` плагин вправе вызвать только для команд, которые сам объявил в `contributes.commands`. Командой плагина считается объявленная, а не та, чей id начинается с его id: id плагина может содержать точку (плагин `a` и плагин `a.b`), а встроенный `shell` объявляет `terminal.copy` и `layout.*`. `Dispatcher` сверяется со списком `plugins.list`, который у окна уже есть (`PluginService`; `roostd` то же знает как `PluginRegistry::CommandOwner`); чужую или неизвестную команду он отвергает `InvalidParams` с причиной («a plugin sets the keys of the commands it declares in its own contributes.commands») до `roostd`, файл не тронут. Плагину при этом разрешены любая клавиша, свободная или занятая другой командой (она выигрывает, как последняя запись файла, без предупреждения окна), и своя команда с любым id; чужой набор клавиш он не правит. Окно без плагина меняет клавиши любой команды.

  Чей это вызов, определяется так (`CallOwners`, `src/qml_api/calling_context.hpp`): плагин называет `PluginLoader` для контекста каждого экземпляра панели и страницы настроек, которую он создал; кроме того, QML-файл под каталогом плагина считается его кодом, даже если его создал не загрузчик (синглтон модуля плагина, `qmlImportPath`, создаётся в корневом контексте движка); и если среди JS-кадров, которые идут сейчас, есть кадр плагина, вызов его (страница плагина, которая зовёт функцию окна, остаётся страницей плагина). Ответ, который приходит позже, кадров не имеет: вызов, сделанный в колбэке, определяется по тому, где колбэк написан. Поэтому помощники окна, которые пишут клавиши (`setKeys`, `removeKey`, `resetKeys` в `SettingsWindow.qml`), спрашивают `Roost.callerPlugin()` при входе и отказывают плагину, зовёт ли он свою команду или чужую: свои клавиши плагин ставит через `Roost.call("keymap.setCommand", …)`. «Окно» здесь — код самого окна настроек и оболочки.

  Это не граница безопасности: код плагина работает в том же движке QML, что и окно, и может достать его объекты (`Window.window`, `Qt.createQmlObject`) и написать любую функцию. Правило защищает от ошибки плагина, который по недосмотру правит чужую команду, а не от враждебного плагина.
- `id` панели в манифесте — имя внутри плагина: непустое, из строчных латинских букв, цифр, `_` и `-` (как id плагина, но без `.`). Окно строит полный id типа панели как `<id плагина>.<имя>`: `list` в плагине `sessions` — панель `sessions.list`; полный id используют слоты окна, связи и `CreatePanel`. Имя с точкой или другим недопустимым символом — проблема загрузчика (панель не создаётся, остальные панели плагина грузятся). Имя без точки, а id плагина уникален, поэтому панели разных плагинов не пересекаются: `a.b` с именем `c` и `a` с именем `b.c` дали бы один тип `a.b.c`, и второе имя отвергается.
- QML-панели (`contributes.panels`) грузит окно (`PluginLoader`): у плагина один контекст QML, у типа панели один `QQmlComponent` из файла `qml`, у каждого экземпляра свой контекст. Корень панели — `Item`; необязательные свойства `pluginId` и `instanceId` получают id плагина и id панели в раскладке окна (`CreatePanel(panelId, instanceId)`; у слотов фиксированной раскладки это `list` и `terminal`) до `Component.onCompleted`. Необязательные числовые свойства `minimumWidth` и `minimumHeight` корня говорят, насколько узким и низким может быть слот панели: окно читает их в `PanelSlot.qml` и не даёт сплиту сжать слот меньше (без свойства или с числом не больше 40 — 40). Размер в документе раскладки они не меняют, пока разделитель не тянут: перетаскивание пишет показанные размеры. Входы и выходы панели — обычные свойства; каждый заявленный в манифесте вход и выход должен быть свойством корня, иначе это проблема загрузчика (панель всё равно создаётся); `SessionRef` — `{agent, id}` или `null`. Манифест панелей проверяет само окно, `roostd` проверяет только, что `panels` — массив: запись — объект, `id` — имя панели (правило выше), `qml` — непустая строка, путь внутри каталога плагина (по тексту, как путь бэкенда), `inputs` и `outputs`, если есть, — объекты, файл существует и компилируется, имя не повторяется в плагине (вторая панель с тем же именем — проблема), корень — `Item`. Сломанная панель отключает только себя: причина идёт в лог окна и в список проблем загрузчика, а не в `plugins.list`. Изменённый плагин (каталог, версия или `contributes`) выгружается и грузится заново вместе с панелями. Если после выгрузки чего-либо загружается плагин, кеш компонентов сбрасывается (один раз за список), чтобы правки QML читались с диска; компоненты оставшихся плагинов Qt в кеше сохраняет. Неизменённый плагин не трогается, его панели остаются. Экземпляр разбирается в таком порядке: сигнал `PanelAboutToBeDestroyed` (панель ещё жива), владелец вызовов, корень, контекст; через `deleteLater` не удаляется, корень снаружи не удаляют (только `DestroyPanel`), окно не разбирает панель изнутри её JS-вызова или обработчика события; у выгружаемого плагина `CreatePanel` ничего не отдаёт, в том числе из слота `PanelAboutToBeDestroyed`. Ждущие вызовы разобранной панели не отвечают никогда.
- Окно настроек (`src/roost/SettingsWindow.qml`; страницы плагинов ему отдаёт `roost::SettingsPages`, `src/roost/settings_pages.hpp`): одно окно верхнего уровня, `Main.qml` создаёт его один раз; закрытие его прячет, повторное открытие поднимает то же окно. Открывает его команда `shell.settings` (§16): `Cmd+,` и пункт «Settings…» меню на macOS, кнопка «Settings…» панели инструментов на Linux. Меню на macOS — родное: у `MenuItem` Qt Quick Controls роли нет, а Cocoa-плагин Qt по тексту пункта («Setting», «Preferences», «Options», «Setup», «Config») считает его настройками приложения и переносит в меню приложения (строки есть в `libqcocoa`; на живом окне не проверено). Qt обнуляет высоту родного `MenuBar` (`QQuickMenuBarPrivate::createNativeMenuBar`), но неявную оставляет, поэтому строка `menuBarLoader` в `Main.qml` берёт высоту из `item.height`: родное меню места в окне не занимает, а в offscreen-тестах меню остаётся в окне над баннером (высоту родного меню на живом окне не проверяли).
  - Две панели: слева список категорий (`categoryList`), справа страница выбранной со своей прокруткой (`settingsScroll`; страница открывается сверху). Порядок: Appearance (тема, шрифты терминала и окна, цвет кольца фокуса), Keys, Updates, затем по категории на каждый плагин со страницей настроек, по заголовку. Встроенные категории перечислены в одном месте, `builtinCategories` в `SettingsWindow.qml`; новая встроенная категория (список плагинов, #349) добавляется туда и страницей в правой панели. Категории «Plugins» пока нет. Видна только страница выбранной категории; остальные не занимают места и не берут Tab. Выбранная категория помнится, пока работает приложение; первый раз окно открывается на Appearance. Если страница выбранного плагина исчезла (плагин выгружен), показана Appearance. Команда `shell.settings` принимает необязательные `args` (§16): `{category: "appearance"|"keys"|"updates"}` или `{plugin: "<id>"}`; без `args` окно открывается на последней выбранной категории, неизвестная категория или плагин без страницы оставляют выбор как был и пишут одно предупреждение. Клавиатура: Up и Down в списке выбирают категорию, страница меняется сразу; Tab уходит из списка в страницу и идёт по её элементам, Shift+Tab назад, Tab с последнего элемента возвращается в список (порядок Tab — порядок элементов в окне, список первый). Строки списка называются для вспомогательных технологий заголовком категории (`Accessible.role: ListItem`), у списка имя «Settings categories».
  - Категории Appearance и Updates (A17, раньше один общий раздел) — документ `settings` (§8): тема (id, которые знает окно; сейчас `default`), семейство и размер шрифта терминала (семейство — выпадающий список: первая строка «System monospace (<имя>)» — умолчание, ключ убирается; дальше установленные моноширинные семейства без скрытых, то есть без имени с точкой. Имя можно набрать: неустановленное или не моноширинное сохраняется, тема его не берёт и пишет проблему. Сохранённое семейство, которого нет в списке, показывается с пометкой «(not installed)», пустое или из одних пробелов — умолчание. Escape в тексте возвращает показанное значение и ничего не пишет. Уход из бокса без правки текста ничего не пишет: бокс показывает документ, даже если тот за это время изменился. Список читается при первом открытии выпадающего списка после открытия окна и держится до закрытия окна: первое чтение медленное (каждое семейство проверяется на моноширинность, шрифты загружаются), повторное быстрое, новый шрифт виден после повторного открытия окна. Пока список открыт или в тексте стоит фокус, обновление документа поле не переписывает, оно показывает новое значение после закрытия списка), размер шрифта окна, цвет кольца фокуса (`settings.focusColor`, ниже), переключатель «Check for updates» (`settings.updates.check`, §17) — он один во вкладке Updates, остальное в Appearance. Правка поля — один `store.patch` одного ключа (`{uiFontSize: 14}`, `{terminalFont: {size: 15}}`, `{updates: {check: false}}`), правки разных ключей из двух окон остаются обе; пустое поле удаляет ключ (значение по умолчанию), последний ключ `terminalFont` уносит и сам объект (`terminalFont: null`, а не `{}`); текст, не являющийся числом в поле размера, правкой не считается, поле возвращается к значению; так же поле возвращается к хранимому значению, когда запись не удалась, а причина остаётся под полями. Документ и таблица клавиш читаются при первом показе окна; пока `roostd` не подключён или чтение не удалось, под полями причина, и чтение повторяется при каждом подключении. Под каждой строкой Appearance и Updates одна строка пояснения приглушённым цветом (`textMuted`): что настройка делает и какие значения допустимы («Size of the text in terminals, 6-72.»); тексты лежат в `SettingsWindow.qml` рядом со строками, у страницы плагина свои. Семейство шрифта терминала — не поле, а список с набором текста (`FormComboBox` с `editable`, `terminalFamilyBox`): первая строка «System monospace (<семейство>)» (умолчание, `Roost.theme.defaultTerminalFont`; выбор или набор этой строки убирает ключ `family`, как пустое поле), дальше установленные моноширинные семейства (`InstalledMonospaceFamilies()` рядом с `IsFixedPitch`, `src/terminal/renderer.hpp`; `Roost.theme.monospaceFamilies()` для QML): `QFontDatabase::families()`, оставлены только те, у которых `IsFixedPitch`, без скрытых (имя с точки, как `.SF NS Mono` на macOS). Список строится при каждом открытии, а не при старте окна: на Linux семейств сотни, и проверка каждого не бесплатна; до первого открытия в списке только умолчание и хранимое семейство. Выбор из списка пишет `{terminalFont: {family}}` одним `store.patch`. Имя можно набрать: Enter или уход из списка пишет набранное как есть, и семейство, которого нет или которое не моноширинное, остаётся прежней проблемой («is not an installed monospace font») с «In use». Хранимое семейство, которого нет в списке (шрифт удалили, файл правили руками), стоит второй строкой с пометкой «<имя> (not installed)» (`Roost.theme.isMonospaceFamily`: то же правило, что у темы, общее имя `monospace` не помечается), так что список не показывает молча другую строку. Размер остаётся полем. Пустое поле размера показывает значение по умолчанию серым: «default: 13 pt». Значение берётся из `Roost.theme.defaultTerminalFont` и `Roost.theme.defaultUiFont` (шрифты, которые тема прочитала один раз при старте; только для показа), а не из шрифта в действии и не зашито: системный шрифт на каждой машине свой, при его смене подсказка меняется после перезапуска. Пока ключ хранится, подсказка всё равно называет умолчание, а не хранимое значение. Размер пишет `Theme::sizeText`: `13 pt`, дробь без хвоста (`13.5 pt`), шрифт в пикселях — `17 px` (QML не отличает размер в пикселях от размера в пунктах: даёт оба). Если хранимое значение не применено (семейство не установлено или не моноширинное, размер вне 6–72, ключ не того типа), поле (у семейства — список с набранным именем) оставляет набранный текст, под ним причина, а следом приглушённая строка «In use: <семейство> / <размер>» называет шрифт, которым пользуются на самом деле (`Roost.theme.terminalFont` или `Roost.theme.uiFont`, размер — `Theme::sizeText`); строка есть только пока у ключа есть проблема настройки. Рядом с полем, пока в документе есть его ключ в любом виде, в том числе неверного типа, кнопка «Reset» (то же, что пустое поле: ключ уходит); такая же у размера окна и у цвета кольца. Если `terminalFont` хранится не объектом, «Reset» обоих полей шрифта терминала убирает весь `terminalFont`; если объектом, «Reset» семейства или размера убирает только свой ключ. У цвета кольца «Reset» есть при любом хранимом `focusColor` (не объект, `custom` без `preset`) и убирает `focusColor`. Цвет кольца фокуса — «Focus ring color»: список Base, Contrast, Custom, рядом с которым для Base и Contrast приглушённо стоит их цвет (`Roost.theme.focusBaseText` — `focus` самой темы, `Roost.theme.focusContrastText` — `FOCUS_CONTRAST_COLOR`), а при Custom — поле `#rrggbb`; под строкой при любом пресете ряд из десяти цветных кружков (`FOCUS_SWATCHES`, `src/core/theme_source.hpp`, в QML — `Roost.theme.focusSwatches`): Base и Contrast темы по умолчанию и восемь цветов, каждый из которых держит все пары `FOCUS_PAIRS` на ней (`TheSwatchesAreTheDocumentedSetAndHoldTheContrast`). Диалога выбора цвета в проекте нет, нового модуля Qt тоже: кружок — одно действие. Клик, Пробел или Enter на кружке пишет одним `store.patch` `custom` с его цветом, а при пресете не Custom ещё и `preset: custom` (`{focusColor: {preset: custom, custom}}`), как и поле, не проверяя контраст; кружок цвета, который в действии (`Roost.theme.focus`), отмечен кольцом внутри, ряд — одна остановка Tab (входит на кружок в действии или на первый), стрелки ходят внутри ряда, Enter с автоповтором выбирает один раз; для скринридера ряд — группа «Focus ring color», имя кружка — hex, у цветов Base и Contrast — «Base (#…)» и «Contrast (#…)», пояснение «Picking it makes the preset Custom» есть, пока пресет не Custom; кольцо фокуса снаружи, как у остальных элементов формы; предупреждение о контрасте то же, что у поля. Выбор пишет `{focusColor: {preset}}`, а Custom без сохранённого цвета ещё и `custom` с цветом, который кольцо имеет сейчас; поле пишет то, что набрано, одним ключом `custom` (пустое поле удаляет его, последний ключ уносит объект). Проблемы настроек, которые читает тема (`Roost.theme.settingsProblems`), показаны под полем своей настройки: ключ `terminalFont` — под полями шрифта терминала, `uiFontSize` — под полем размера окна, `focusColor` — под строкой «Focus ring color». Списка выключенных плагинов в окне нет: ключ `plugins.disabled` (выше, «Встроенные фичи…») правится в `settings.json` вручную и действует после перезапуска `roostd`; страницы есть только у загруженных плагинов.

Значения страница хранит в документе своего плагина под ключом `settings` и пишет патчем: `Roost.store.patch(pluginId, {settings: {note: "…"}})`.

- Режим разработки, `roost --dev` (только в окне с плагинами, не с `--session`): `PluginWatcher` (`src/roost/plugin_watcher.hpp`) следит за каждым `*.qml`, `*.js` и `qmldir` под каталогом загруженного плагина, за самими каталогами и за родителем каталога плагина (не рекурсивно; плагин с пустым или относительным каталогом пропускается) (`QFileSystemWatcher`; рецепт тот же, что у keymap, §16: событие каталога возвращает под слежение файл, замещённый через `rename`, и подхватывает новые файлы). Через 100 мс после последнего события плагина вызывается `PluginLoader::Reload(id)`: перезагружается только этот плагин, разбор как у изменённого (экземпляры панелей с `PanelAboutToBeDestroyed`, компоненты, контекст, проблемы плагина), кеш компонентов сбрасывается, плагин грузится заново с тем же объявлением; ждущие вызовы его панелей не отвечают. Событие, после которого время изменения, размер и время смены прав пути те же (чтение файла самим перезагрузчиком), перезагрузку не запускает. Удалённый файл — одна перезагрузка (панель, которой он нужен, становится проблемой загрузчика), записанный снова — ещё одна. Удалённый каталог плагина — одна перезагрузка (все его панели становятся проблемами); когда каталог создан снова, даже спустя время, событие родителя запускает перезагрузку, и плагин возвращается. Всего отслеживается не больше 256 путей (каталоги, в том числе родители, первыми); что не поместилось, перечислено в `qWarning` один раз на набор, остальное работает. Теряется оконное состояние панелей плагина (выбор в списке и т. п.); что панель держит в `Roost.store` или в `roostd`, возвращается. Манифест и нативные библиотеки не перечитываются: `roostd` читает `plugin.json` при старте, поэтому правка манифеста требует перезапуска `roostd`; окно переподключится, и загрузчик перезагрузит изменённый плагин как обычно. `Reload` нельзя вызывать из JS-вызова панели: вызывает его таймер.
- Сборка раскладывает встроенные плагины в `build/<пресет>/roost-plugins/<id>/`: `plugin.json`, `qml/` (если есть; в нём `qml/<URI>/` с собранным QML-модулем на C++, если он есть) и `backend/` (если есть). Демон находит их сам: `build/<пресет>/bin/roostd` ищет `../roost-plugins`, переменная не нужна. Это копии: CMake копирует `plugin.json` и файлы QML при конфигурации, поэтому `roost --dev` следит за копией в `build/<пресет>/roost-plugins`, а не за файлами в `plugins/`. Правка `plugins/<id>/qml/*.qml` доходит до окна после `cmake --build --preset dev`.
- Поиск: каталоги из `ROOST_PLUGINS_PATH` (через `:`, только абсолютные пути), а если переменная не задана, пуста или в ней нет ни одного абсолютного пути — встроенный каталог пакета; затем `<каталог состояния>/plugins`; каталог, названный дважды, просматривается один раз. В каждом — подкаталоги с `plugin.json`, по имени с учётом регистра: заглавные раньше строчных. Порядок поиска и есть порядок загрузки. Встроенный каталог (`BundledPluginsDirectory`, `src/roostd/manifest.cpp`) — первый существующий из трёх путей от каталога бинарника `roostd`, в этом порядке; нет ни одного — его нет в поиске. Пути: `<каталог roostd>/../Resources/roost-plugins` — в `roost.app` это `Contents/Resources/roost-plugins` (`roostd` лежит в `Contents/MacOS`); `../lib/roost/plugins` — в AppImage `usr/lib/roost/plugins` внутри монтирования образа (`roostd` — `usr/bin/roostd`, его запускает `$APPIMAGE --roostd`, §11), так же в установленном `usr/` (`cmake --install`, Linux); `../roost-plugins` — в дереве сборки `build/<пресет>/roost-plugins` (`build/<пресет>/bin/roostd`). Код плагина (бэкенд `claude-adapter`, библиотека QML-модуля) лежит в тех же каталогах плагинов; в `.app` это симлинки на `Contents/MacOS` и `Contents/PlugIns/roost`. Заданная переменная заменяет встроенный каталог: чтобы сохранить встроенные плагины, перечисли его в ней. Второй плагин с тем же `id` не загружается: плагин пользователя с `id` встроенного проигрывает ему, причина — в `problems` ответа `plugins.list`; чтобы поставить свой плагин на место встроенного, встроенный выключают (`plugins.disabled`, выше), а свой ставят под другим `id`: `plugins.disabled` пропускает все плагины с этим `id`, и плагин с `id` встроенного выключился бы вместе с ним.
- Заготовка плагина с QML-панелью — `templates/plugin-qml/` (README с шагами и с добавлением бэкенда, на русском и английском); сборка её не трогает.
- Манифест проверяется при загрузке (`src/roostd/manifest.hpp`): `api` совпадает с API демона, программа бэкенда и `settings` (путь или `qml` объекта `{qml, title}`) — пути внутри каталога плагина, `title` — строка (проверка по тексту пути, симлинки не раскрываются: код плагина и так работает от имени пользователя), хоткей назначен на команду того же плагина, у плагина с агентами есть бэкенд. Id агента — как id плагина; агент, объявленный вторым плагином, остаётся за первым. Хоткей команды, проигравшей конфликт, тоже не действует. Неизвестные ключи игнорируются. Плагин с битым манифестом не загружается, а остальные загружаются; отказ и каждый проигравший конфликт сохраняются как проблема для пользователя.
- Бэкенд (`src/roostd/backend.hpp`) запускается в каталоге плагина, в своей сессии: Ctrl-C в терминале демона до него не доходит. Протокол — JSON-RPC 2.0, одно компактное сообщение на строку в stdin и stdout; stderr бэкенда идёт в stderr демона. Демон шлёт запросы и ждёт ответов без таймаута; уведомления бэкенда принимает; на запрос от бэкенда отвечает только `bus.subscribe` и `bus.unsubscribe` (ниже) и `store.get` и `store.patch` для его собственного документа (ниже), остальные — `MethodNotFound`. Закрытый stdin значит «завершись»: через секунду после этого процесс убивается.
- Шина со стороны бэкенда: бэкенд подписывается запросом `bus.subscribe {pattern}` (любой допустимый шаблон, `*` тоже; плагины доверенные, §12), снимает подписку `bus.unsubscribe {subscription}` и получает события уведомлениями `bus.event {subscription, name, payload}`; ошибки те же, что у сокета (§4). Это нужно бэкенду плагина `notifications` (M8): он видит `session.stateChanged`, пока окна нет. Свои события бэкенд публикует уведомлением `bus.publish {name, payload?}`: демон публикует его как есть, только если `name` начинается с `<id плагина>.`; чужой префикс, недопустимое имя и событие больше кадра отбрасываются записью в лог. Бэкенд публикует только под своим id: демон не резервирует корни событий демона от id плагинов, потому что плагины доверенные (§12). Подписки бэкенда живут, пока жив его процесс, и снимаются, когда он кончился (упал, не запустился, демон сдался после неудач или `roostd` завершается), в том числе когда бэкенд не читает свой stdin и очередь записи ему перевалила за `MAX_UNSENT_BYTES` (как сокет, он обрывается): демон их не восстанавливает, перезапущенный бэкенд подписывается заново (иначе событие дошло бы до него по подписке умершего процесса и по новой, дважды), а события за время простоя теряются. Протокол целиком — §4.
- Уведомления рабочего стола (M8, `src/roost/window_notifications.{hpp,cpp}`): при `settings.desktop` (по умолчанию включено) бэкенд `notifications` для события из `settings.events` публикует `notifications.show {title, body, agent?, session?}`. `title` — название сессии (id, если названия нет), `body` — «needs you», «is done» или «failed»; `agent` и `session` — адрес сессии, их нет у `notifications.test`, который публикует `{title: "roost", body: "Test notification from roost"}`. Команды пользователя запускаются независимо от `desktop`. Показывает уведомление окно, не бэкенд: ему нужны экран и значок приложения. Окон может быть несколько, а показать нужно одно, поэтому окно, получив фокус клавиатуры (`QGuiApplication::focusWindowChanged` на своё главное окно, а не `applicationStateChanged`: тот не говорит, какое окно в фокусе), публикует `shell.windowFocused {window}`. `window` — случайный id процесса (`QUuid`), он не меняется, пока окно живо. Каждое окно помнит последний `window`, который услышало в этом событии, свой тоже: `roostd` отдаёт события всем подписчикам в одном порядке, так что окна согласны. `notifications.show` показывает только окно, у которого последний `window` — свой. Окно, не слышавшее ни одного `shell.windowFocused` с запуска (оно стартовало после чужого фокуса и само ещё не в фокусе), не показывает ничего. При закрытии окна ничего не публикуется. При потере связи с `roostd` последний id забывается (события пропущены), а окно, которое в фокусе или было последним в фокусе к моменту потери связи, после возврата связи публикует своё событие снова. Окно в фокусе не показывает уведомление о сессии, которую в этот момент показывает терминал этого окна (`TerminalItem.session`, `agent` и `id` совпадают); окно не в фокусе показывает любое. Отказ: окон нет — уведомления нет, команды всё равно запускаются. Клик по уведомлению поднимает окно (`raise()`, `requestActivate()`) и запускает команду окна `sessions.open {agent, id}` (`16-keymap.md`, «Команды окна»); у уведомления без сессии клик только поднимает окно. Показывает уведомление `DesktopNotifier` (`src/roost/desktop_notifier.hpp`): по реализации на платформу, выбранной при сборке; на Linux — `org.freedesktop.Notifications.Notify` по сессионной шине D-Bus (`desktop_notifier_linux.{hpp,cpp}`, отдельная библиотека `roost_notifier_linux`: QtDBus линкуется только в `roost` на Linux и в её тест) со значком из `share/icons/hicolor/128x128/apps/roost.png` рядом с `bin/` (иначе имя `roost` из темы), подсказкой `desktop-entry` = `roost` и действием `default`; `NotificationClosed` и смена владельца службы (`QDBusServiceWatcher`) забывают id уведомлений; сигнал `ActivationToken` кладёт токен кликнутого уведомления в `XDG_ACTIVATION_TOKEN` на время `Activated` (Wayland: `requestActivate()` берёт фокус по токену); шины или службы нет — одно предупреждение в лог окна и ничего не показано. На macOS — `UNUserNotificationCenter` (`desktop_notifier_macos.{hpp,mm}`, отдельная библиотека `roost_notifier_macos`, ARC; линкует `UserNotifications`) со значком из бандла (`roost.icns`). Работает только внутри `roost.app`: у процесса без бандла (`build/<preset>/bin/roost`) нет `bundleIdentifier`, а центр уведомлений в таком процессе бросает исключение, поэтому там первый `Show` пишет одно предупреждение «desktop notifications need roost.app» и ничего не показывает. Разрешение (только `Alert`: звука нет) просится при первом `Show`, а не при старте окна: этот `Show` ждёт ответа, поток GUI не блокируется, а следующие встают в очередь, в которой остаются три последних (старые отбрасываются); отказ или ошибка — одно предупреждение и ничего не показано до следующего запуска (разрешение меняется в Системных настройках → Уведомления). Запрос на каждое уведомление: идентификатор `roost-<токен>-<id>` (`src/roost/notification_ids.{hpp,cpp}`, собираются на всех платформах; токен — случайный `QUuid` процесса), `userInfo` `{roostId: id}`. Делегат центра, поставленный при создании, показывает баннер и в списке уведомлений и когда roost на переднем плане (окно уже решило, что это уведомление нужно показать); клик по действию по умолчанию отдаёт `Activated(id)` в потоке GUI, и только для идентификатора с токеном этого процесса и совпавшим `userInfo`. При двух процессах roost клик доходит до показавшего уведомление, только если система доставила его туда; иначе он игнорируется. При выходе уведомления процесса снимаются из Центра уведомлений (доставленные и ожидающие), так что клик по ним после выхода невозможен; уведомление упавшего roost может остаться, и клик по нему запускает roost, но сессию не открывает.
- Документ бэкенда: запросы `store.get {}` и `store.patch {patch}` (RFC 7386) относятся к документу его плагина; `plugin` в параметрах можно опустить или назвать им свой id, чужой id — `InvalidParams` с причиной. Ответы, ошибки и события `store.changed` те же, что у сокета (§4, §8), так что бэкенд, подписанный на `store.changed`, видит и правки окна, и свои. Писать лучше `store.patch` своего ключа: ключи, которые пишет пользователь, остаются нетронутыми. `store.set` бэкенду недоступен.
- Страница настроек плагина `notifications` (`plugins/notifications/qml/NotificationsSettings.qml`, категория «Notifications» окна настроек, `contributes.settings`): переключатель «Desktop notifications» (`settings.desktop`), три переключателя событий «Needs you», «Done», «Failed» (`settings.events`) и список команд пользователя. Строка команды — имя, текст `run` (моноширинный), три флажка событий, переключатель «Enabled», кнопки «Test» и «Remove» и последний результат из `results.<имя>` («exit 0 · 12:03», «timeout · 12:03», хвост stderr в три строки, «Show all» раскрывает его целиком); «Add command» добавляет строку с именем «command N» и переводит на неё клавиатуру; строка только на странице, в документ команда попадает, когда её `run` впервые стал непустым (с именем и событиями), пока `run` пуст, строка пишет «Not saved until it has a command», а «Test» выключена; после «Remove» клавиатура идёт на имя следующей строки (у последней — предыдущей, без строк — на «Add command»). Документ пустой — страница показывает умолчания бэкенда (`backend/settings.hpp`: desktop включён, события `blocked` и `failed`, команд нет); команда без `events` показана с тремя флажками, пишется всегда явный список. Скаляр пишется патчем своего ключа, любое изменение списка команд — патчем всего массива `commands` (RFC 7386 заменяет массив целиком); `results` страница только читает. Текстовое поле пишется по `editingFinished` (Enter или уход фокуса), пустое или занятое имя отвергается сообщением под строкой, прежнее имя остаётся. Страница идёт за `store.changed` (второй писатель, `results` бэкенда), не трогая поле, в котором пользователь напечатал и не закончил (флаг «правлено» ставит `onTextEdited`, `editingFinished` пишет только правленое поле; поле с фокусом, но без правки, идёт за документом); строки сопоставляются с командами документа по имени, а не по месту: строка хранит своё состояние (набираемый текст, последний «Test», «Show all») при добавлении и удалении других команд другим писателем; команда пишется как её исходный объект с четырьмя полями страницы (`name`, `run`, `events`, `enabled`) поверх, так что неизвестные ключи, неизвестные имена событий и элементы массива, не являющиеся объектами, сохраняются на своих местах; запись, на которую ответ не пришёл за 10 с, бросается, документ читается заново (одно предупреждение); пока ответ на запись не пришёл, документ из `store.changed` не берётся, после последнего ответа он читается заново. «Test» вызывает `notifications.test {name}`, кнопка выключена, пока не придёт `results.<имя>` с новым `at` (и пока не отвечена запись), ошибка ответа показана под строкой. Контролы свои, на токенах `Roost.theme` (плагин не импортирует контролы окна); Tab проходит по ним в порядке чтения.
- Встроенный плагин `notifications` (M8, `plugins/notifications`): бэкенд (`backend/notifier.{hpp,cpp}`, `backend/command_runner.{hpp,cpp}`) подписан на шину `session.*` и `store.changed` и при переходе сессии в `blocked`, `done` или `failed` запускает команды пользователя и публикует `notifications.show` (абзац выше), пока окна нет и сколько бы их ни было. Манифест: страница `contributes.settings` (Settings → Notifications) и команда `notifications.test`. Документ плагина `notifications`: `settings` пишет пользователь (страница, `store.patch`, клиент сокета), бэкенд читает его при старте и при каждом `store.changed` плагина; `results` пишет только бэкенд.
  - `settings`: `{desktop, events, commands}`. `desktop` (по умолчанию `true`) — публиковать ли `notifications.show`; `events` (по умолчанию `["blocked", "failed"]`) — события, о которых уведомлять вообще (и окно, и команды); `commands` — массив `{name, run, events?, enabled?}`: `name` уникально, `run` — текст `bash -c`, `events` (по умолчанию все три) — подмножество `blocked`, `done`, `failed`, `enabled` (по умолчанию `true`). Команда запускается, если событие есть и в `settings.events`, и в её `events`, и она включена. Поле не того типа, неизвестное имя события и команда без имени, без `run` или с занятым именем пропускаются с одним предупреждением в stderr бэкенда, остальное берётся; нет `settings` или поля — умолчание (`backend/settings.hpp`). Пропущенное поле не того типа даёт умолчание, а оно шире написанного: `"events": "blocked"` уведомляет обо всех трёх событиях команды (`settings.cpp`, `ParseEvents`), `"enabled": "false"` оставляет команду включённой.
  - Событие — сессия, у которой состояние (`session.stateChanged`) сменилось на `blocked`, `done` или `failed`. Адаптеры шлют `session.stateChanged` только при смене (первый список адаптера — база и ничего не шлёт), поэтому сессия, которой бэкенд не видел, тоже смена: первое же `blocked` уведомляет. То же состояние повторно не уведомляет. `session.removed` забывает сессию (её нет в списке адаптера: `plugins/claude/backend/adapter.cpp`), поэтому сессия, которая выпала из списка и вернулась в состоянии `blocked`, `done` или `failed`, уведомляет снова.  `session.adapterStarted` — сессии перезапущенных агентов, чтобы состояние, оставшееся с прошлого запуска, не поглотило следующую смену.
  - `results.<name>` — итог последнего запуска команды `name`: `{exitCode | error, stderr, at, event}`. `exitCode` есть у команды, которая завершилась, `error` — у той, что нет: `timeout`, `failed to start` или `crashed` (сигнал, не наш); второго ключа нет. `stderr` — последние 2000 байт, начиная с границы символа; `at` — миллисекунды с эпохи; `event` — `blocked`, `done`, `failed` или `test`. Итог пишется патчем `{results: {<name>: …}}`, поэтому `settings` бэкенд не затирает; итоги команд, которых больше нет в `settings`, удаляются при изменении `settings` и при старте (первый `ApplyDocument`). Итог команды, которая в момент очистки идёт или стоит в очереди, пишется после очистки и остаётся; очередь хранит прежний `run`. У `failed to start` в `stderr` лежит `QProcess::errorString()`.
  - Запуск (`CommandRunner`): `bash -c <run>`, рабочий каталог — домашний (если `HOME` не каталог, команда идёт в каталоге плагина), stdout сброшен, stderr читается в `results`, на stdin — JSON контракта ниже, после него stdin закрыт. Каждая команда в своей сессии (`setsid()` в модификаторе дочернего процесса) и группе процессов, сигналы по умолчанию. Пределы: 10 с на запуск, по истечении группа убивается целиком (`SIGKILL`; итог `timeout`); одновременно не больше 4 запусков, остальные ждут в очереди из 64 по порядку; запуск сверх очереди отбрасывается с предупреждением в stderr бэкенда и итога не оставляет. Команды умирают вместе с бэкендом, как бы он ни кончился (обычная остановка, падение, `SIGKILL` от `roostd`), пока команда (её первый процесс) жива: фоновые процессы, оставшиеся после её конца (`run: "foo &"`), не убиваются, как и раньше. У каждой команды есть сторож (`plugins/common/child_lifeline`) — лишний процесс в группе команды, форк до `exec`; он читает конец канала, второй конец которого держит только бэкенд, и по EOF убивает группу (`SIGKILL`), если команда ещё жива, а если команда уже кончилась — молча выходит. Из-за этого лишнего потомка команда, которая ждёт всех своих детей до `ECHILD`, ждёт до тайм-аута. Сторож наследует обработчики сигналов бэкенда (`ResetSignalHandlers` применяется после модификатора) — это безвредно; в `ps` он виден вторым `notifications-backend`; реагирует за 100 мс. Прецедент — страж процессов в тестах (`tests/helpers/process_lifeline`).
  - Проверка: команда `notifications.test {name?}` (кнопка «Test» страницы, `commands.run`) запускает команду `name`, даже выключенную, или все включённые, независимо от их `events` и от `settings.events`, с `ROOST_EVENT=test` и сообщением «Test notification from roost»; при `desktop` публикует `notifications.show` без сессии. Отвечает `{ran: [имена]}` сразу, не дожидаясь итога: имена запущенных и поставленных в очередь, отброшенные в них нет. Имя, которого нет в `settings`, — `InvalidParams`. Итог проверки попадает в `results` с `event: "test"`.
  - Контракт команды пользователя, версия 1 (`ROOST_NOTIFY_VERSION=1`; `Notifier::MakeJob`). Команда получает окружение бэкенда и переменные ниже, а то же самое одним компактным JSON-объектом — на stdin (ключи stdin — те, что в таблице):

    | переменная | ключ stdin | значение |
    |---|---|---|
    | `ROOST_NOTIFY_VERSION` | `version` | `1` (в JSON число) |
    | `ROOST_EVENT` | `event` | `blocked`, `done`, `failed` или `test` |
    | `ROOST_AGENT` | `agent` | id агента; пусто у `test` |
    | `ROOST_SESSION_ID` | `sessionId` | id сессии; пусто у `test` |
    | `ROOST_SESSION_TITLE` | `title` | название сессии; пусто, если названия нет (id сюда не подставляется), и у `test` |
    | `ROOST_SESSION_CWD` | `cwd` | рабочий каталог сессии; пусто, если не известен, и у `test` |
    | `ROOST_STATE` | `state` | состояние сессии (`blocked`, `done`, `failed`); пусто у `test` |
    | `ROOST_MESSAGE` | `message` | «<название> needs you», «<название> is done» или «<название> failed» (id, если названия нет); у `test` — «Test notification from roost» |

    Правило версии: в пределах версии могут добавляться новые переменные и ключи, поэтому команда не должна падать на незнакомых ключах stdin; удаление переменной или ключа и смена значения (набор значений `ROOST_EVENT`, формат `ROOST_MESSAGE` как данные, смысл пустоты) поднимают `ROOST_NOTIFY_VERSION`. Тексты `ROOST_MESSAGE` — для показа человеку, разбирать их не нужно: для логики есть `ROOST_EVENT` и `ROOST_STATE`. Данные сессии приходят только этим путём и в текст `run` не подставляются (12-trust.md). Результат (`results`) контракт не включает: его читает страница, а не команда.
  - Пример команды в `settings.commands` (значения только из окружения или stdin, в кавычках; не `bash -c "... $title ..."` с подстановкой):

    ```json
    {"name": "webhook", "events": ["blocked", "failed"],
     "run": "curl -sS -m 5 -X POST -H 'Content-Type: application/json' --fail --data-binary @- https://example.com/hook"}
    ```

    Тело запроса — stdin команды, то есть JSON контракта как есть, и название сессии не попадает в текст команды; вебхук получает название сессии и её рабочий каталог. Если нужен свой текст, его собирают из переменных: `"run": "notify-send -- \"$ROOST_MESSAGE\""` (Linux); значение — аргумент, а не часть текста команды. На macOS: `"run": "osascript -e 'on run argv' -e 'display notification (item 1 of argv) with title (item 2 of argv)' -e 'end run' \"$ROOST_MESSAGE\" \"$ROOST_SESSION_TITLE\""`; текст в `osascript -e` подставлять нельзя (12-trust.md).
- Бэкенд упал, если сам завершился, не запустился или нарушил протокол: строка не JSON-RPC, ответ на чужой id, ответ без `result` и `error`, `error` не объектом, строка длиннее 16 МиБ. Нарушителя демон убивает. Ждущие запросы получают -32003, демон перезапускает бэкенд через 0,5 с, и с каждым падением подряд пауза удваивается, до 30 с. После пятого перезапуска подряд бэкенд остаётся лежать. Минута работы без падений обнуляет счёт.

Цена: JavaScript плагина выполняется в GUI-потоке, и небрежный плагин может подвесить окно. Смягчение — бэкенд-процессы для тяжёлого и оверлей времени кадра в режиме разработки, который называет медленную панель.

## Нативные плагины

Два уровня с разными гарантиями:

| Уровень | Что даёт | Чья гарантия совместимости |
|---|---|---|
| C ABI (`roost/plugin.h`) | вызовы API roost, шина, хранилище, команды | roost: тот же major SDK, minor не выше, чем у roost; в 0.x minor совпадает |
| QML-модуль на C++ | свои QML-типы, модели, `QQuickItem` | Qt: та же major-версия, minor не выше, чем у Qt в roost |

Через C ABI не ходят типы Qt и классы C++. Свои QML-типы плагин отдаёт стандартным QML-модулем (`qt_add_qml_module`), а с roost такой модуль говорит только через `Roost.*`, без заголовков roost.

Qt 6 совместим назад внутри major-версии: «Minor releases are backwards binary and source compatible» (https://wiki.qt.io/Qt-Version-Compatibility). Плагин, собранный с более новым Qt или в другом режиме (debug или release), Qt не загружает (https://doc.qt.io/qt-6/deployment-plugins.html). Отсюда правила для QML-модуля плагина:

- собирать в release против Qt 6.8 — нижней границы, с которой собирается сам roost (`find_package(Qt6 6.8 ...)` в `CMakeLists.txt`); такой модуль грузится в roost на любом Qt 6.8 и новее внутри Qt 6;
- пользоваться только публичным API Qt: приватные заголовки (`QQuickItemPrivate`, внутренности scene graph) гарантией совместимости не покрыты;
- свою копию Qt не класть: модуль использует Qt из бандла roost. Что вторая копия при этом не появляется, проверяется в M9 (§14).

Манифест:

```json
"native": { "library": "lib/libfoo", "sdk": "0.1", "qt": "6.8", "qmlImportPath": "qml" }
```

| Ключ | Когда нужен | Что значит |
|---|---|---|
| `library` | есть библиотека на C ABI | путь без расширения, roost добавляет `.dylib` или `.so` |
| `sdk` | вместе с `library` | версия SDK, с которой собрана библиотека |
| `qt` | библиотека или QML-модуль линкуют Qt | версия Qt, с которой они собраны |
| `qmlImportPath` | есть QML-модуль | каталог, который окно добавляет в import path движка |

Пути `library` и `qmlImportPath` проверяются, как путь бэкенда: внутри каталога плагина, по тексту пути.

QML-модуль плагина, без библиотеки на C ABI:

- Работают `qt` и `qmlImportPath`. `qt` — `"MAJOR.MINOR"` без патча, такой же major, как у Qt в roost, и minor не выше. Оба ключа необязательны. `library` и `sdk` пока отказывают весь плагин с причиной в проблемах (до SDK 0.1, M9).
- `roostd` отдаёт `native` в `plugins.list`, только если плагин его объявил; окно не различает отсутствующий ключ и пустой объект: в обоих случаях добавлять нечего. Окно добавляет `<каталог плагина>/<qmlImportPath>` в import path движка после путей, которые там уже были: плагин не подменяет модуль roost, а модуль с одним URI у двух плагинов принадлежит тому, кто раньше в порядке загрузки. Пути стоят до загрузки панелей, поэтому панель делает `import <URI>`.
- Изменение `native` перезагружает плагин, как изменение `contributes`; выгруженный плагин убирает свой каталог из import path. Модуль, который движок уже импортировал, остаётся в нём до выхода: библиотеку модуля Qt держит загруженной, изменённую подхватывает перезапуск окна.
- Рецепт для модуля на чистом QML: `native: {"qmlImportPath": "qml"}`, в `qml/<URI, точки как каталоги>/` лежат `qmldir` (`module <URI>`, строка `Тип 1.0 Тип.qml` на тип) и файлы типов, панель начинается с `import <URI>`. URI не из пространства `Roost.*`: оно у roost.
- Рецепт для модуля на C++ в дереве roost (`plugins/sessions/`): `qt_add_plugin(<цель> CLASS_NAME <URI без точек>Plugin)`, затем `qt_add_qml_module(<цель> PLUGIN_TARGET <цель> URI <URI> VERSION 1.0 OUTPUT_DIRECTORY ${ROOST_<ID>_PLUGIN_DIR}/qml/<URI, точки как каталоги> NO_CACHEGEN SOURCES ...)`. Без `qt_add_plugin` Qt собирает отдельные библиотеку и плагин, и каталог модуля не самодостаточен. Логика лежит в статической библиотеке с `POSITION_INDEPENDENT_CODE ON`, которую линкует модуль и тесты; на ней `qt_extract_metatypes`. Тип из библиотеки регистрируется обёрткой `struct { Q_GADGET QML_FOREIGN(Тип) QML_NAMED_ELEMENT(Имя) }` в отдельном `module/*.hpp`, на который указывает `target_include_directories` модуля. Манифест: `native: {"qt": "6.8", "qmlImportPath": "qml"}`. Тест загружает модуль через `QQmlEngine::addImportPath(<выходной каталог>/qml)`. Гейт плагинов принимает эту форму: цель линкует только Qt и библиотеку плагина.

Загрузка и рукопожатие:

- Нативный код грузится только в окне, через `QLibrary`. Код на стороне демона — бэкенд-процесс.
- `roostd` проверяет ключ `native` вместе с остальным манифестом: плагин не загружается, если major SDK не совпадает, minor SDK выше, чем у roost (в 0.x — не равен), или Qt другой major-версии либо новее Qt в roost. Отказывает весь плагин: QML, библиотека и бэкенд. Причина попадает в проблемы для пользователя, как битый манифест.
- Макрос `ROOST_PLUGIN(...)` экспортирует три функции и больше ничего: `roost_plugin_query` (статическая `roost_plugin_info {struct_size, sdk_major, sdk_minor, id, qt_version, encoding}`), `roost_plugin_init(const roost_host*, ctx**)` и `roost_plugin_shutdown(ctx)`.
- Окно загружает библиотеку и вызывает `query`. Если ответ расходится с манифестом, окно не вызывает `init` и не грузит QML плагина, причина — в проблемах. Загрузка уже исполняет статические инициализаторы плагина, поэтому несовместимость ловит манифест, а `query` её только подтверждает.
- Закрытие: окно уничтожает QML плагина, отменяет его подписки и ждущие вызовы (после этого колбэки плагина не вызываются), затем вызывает `shutdown`. Библиотека остаётся загруженной до выхода. Перезагрузка QML работает как раньше; изменённую библиотеку подхватывает перезапуск окна, состояние и тёплые сессии при этом в `roostd`.

Как растёт API:

- `roost_host {struct_size, sdk_minor, …}` и таблицы функций, которые плагин передаёт в roost, только дописываются в конец. Обёртка проверяет `struct_size` перед вызовом функции из более новой версии; таблицу плагина roost копирует в обнулённую структуру по меньшему из размеров, по образцу libobs (`obs_register_source_s`, https://github.com/obsproject/obs-studio/blob/7cad8fc22ad3ea68e44d056fde57be2fe0f5b719/libobs/obs-module.c).
- Функции хоста — `call(method, payload, cb, user)`, `subscribe(pattern, cb, user)`, `unsubscribe`, `publish(name, payload)`, `post_to_gui(fn, user)`, `log`. Имена методов и схемы — каталог §4: новый метод API — новое имя, а не новый ABI. Отдельные типизированные функции появляются только для горячих путей и тоже дописываются в конец.
- Кодировка данных объявлена в `roost_plugin_info.encoding`. В 0.x это JSON; бинарный формат (FlatBuffers, protobuf) выбирается в M9 по замеру вызовов в GUI-потоке.
- Несовместимое изменение — `roost_host_v2` рядом с v1; v1 обслуживается до следующего major.

Потоки и память:

| Что | Правило |
|---|---|
| `post_to_gui`, `log` | из любого потока; `post_to_gui` вызывает `fn(user)` в GUI-потоке |
| остальные функции хоста | только из GUI-потока; отладочная сборка падает на нарушении, в релизе поведение не определено |
| колбэки `call` и `subscribe` | приходят в GUI-поток и укладываются в бюджет кадра (§9); тяжёлое — в потоки плагина или в бэкенд |
| данные, которые плагин передаёт в функцию хоста | roost копирует до возврата из функции |
| данные в колбэке | живут до возврата из колбэка; плагин копирует, что ему нужно дольше |

Память через границу не освобождается: каждая сторона освобождает только своё.

Один API: сервисы и диспетчер методов окна лежат в `src/api/`, синглтон `Roost` (`src/qml_api/`) и таблица хоста SDK (`src/sdk_host/`) — адаптеры над ним. Тест сверяет, что каждый метод диспетчера доступен и из `Roost`, и через `host->call`. Роли модели `Roost.sessions` совпадают с полями `sessions.list`.

Контракт `Roost` для QML (`import Roost.Api`). Ответ приходит в колбэк последним аргументом: `callback(error, result)` в GUI-потоке. При успехе `error` — `null`, при отказе `error` — `{code, message, data?}` (коды те же, что в протоколе), а `result` не задан. Колбэк всегда вызывается асинхронно, через цикл событий, и никогда внутри самого вызова. Колбэк `Roost.store.get` обязателен (без него вызов ничего не вернёт), у остальных вызовов его можно опустить: отказ без колбэка попадает в лог предупреждением, исключение из колбэка тоже. Если движок QML уничтожен до ответа, колбэк не вызывается.

- `Roost.call(method, params, callback)`: любой метод диспетчера по имени, как `host->call` в SDK; чего в диспетчере нет (`hello`, `session.open`), то `-32601`. `keymap.setCommand` и `keymap.resetCommand` вызов плагина принимает только для команд, которые плагин объявил в `contributes.commands`, иначе `-32602` с причиной.
- `Roost.commands.run(command, args, callback)`.
- `Roost.commands.registerCommand(command, handler)`: даёт команде обработчик в окне, `handler(args)` исполняется при запуске команды (клавишей, палитрой, `run`) без запроса к `roostd`; возвращённое значение — ответ (`undefined` — `null`), исключение — `InternalError`. Возвращает `true`; `false` — пустой id или вызывающая панель выгружается. У команды может быть несколько обработчиков: исполняется последний зарегистрированный из живых. Обработчик живёт, пока жива панель, из чьего контекста вызвана функция (владелец вызовов, правило выше), и снимается при её выгрузке; из QML оболочки — пока живо окно. Не функция вместо обработчика бросает `TypeError`. Имя не `register`: это ключевое слово C++, а moc называет метод так, как он написан. Команду объявляет манифест плагина (`contributes.commands`): там у неё клавиша и место в палитре; `registerCommand` её только исполняет (§16).
- `Roost.sessions` — модель списка сессий всех агентов (`QAbstractListModel`), строки идут в порядке ответа `roostd`, новая сессия добавляется в конец, удалённая (`session.removed`) исчезает из модели как `rowsRemoved`. Свойства: `loaded` (пришёл первый список этого соединения), `unavailable` (массив `{agent, reason}` для агентов, чей адаптер не ответил списком). Сигнал `listed(agent)`: адаптер агента сообщил, что листинг закончен и сессии, которые он изменил, уже переданы (событие `session.listed {agent}`, §7); приходит после загрузки первого списка. `Roost.sessions.refresh(callback?)` запрашивает список заново (`sessions.list`); строки заменяются до вызова колбэка. Пока соединения нет, модель пуста.
- `Roost.store.get(plugin, callback)` отдаёт `{document}`; `Roost.store.set(plugin, document, callback?)`; `Roost.store.patch(plugin, patch, callback?)` возвращает `bool` (`false`, если вызов не удалось сделать: у вызывающего нет контекста, колбэк тогда не вызывается) и сливает `patch` с текущим документом по RFC 7386 (04-protocol.md); сигнал `Roost.store.changed(plugin, document)` приходит для документов, которые уже прочитаны, и при записи из другого окна. Колбэк `get` получает документ таким, каким окно знает его в момент вызова колбэка, если документ уже в кеше окна (прочитан при живой подписке на `store.changed` этого соединения): ответ идёт в колбэк через цикл событий, и `store.changed`, обогнавший его, не откатывается назад старым ответом. Документ не в кеше (до подписки, после разрыва) приходит как ответ `roostd`.
- `Roost.bus.subscribe(pattern, owner, callback)` возвращает id; `callback(name, payload)`. Подписка живёт, пока жив `owner` (объект QML), либо до `Roost.bus.unsubscribe(id)`. `Roost.bus.publish(name, payload, callback?)`.
- Ошибки аргументов `subscribe` (владелец `null`, колбэк не функция, неверный шаблон) бросают `TypeError`; ошибки самих вызовов приходят в колбэк.
- `Roost.bindingKey(event)`: клавиша, которую обработчик `Keys.onPressed` сравнивает с `Qt.Key_*`, на любой раскладке. Принимает `KeyEvent`, возвращает `Qt.Key_*`: `event.key` на латинской раскладке, на нелатинской — клавиша US-раскладки на той же физической позиции (`о` на русской — `Qt.Key_J`, Shift+`б` — `Qt.Key_Less`). Буква приходит заглавной, цифра и символ следуют за Shift. Метод оконный: он ничего не просит у `roostd`, не метод диспетчера и в `host->call` его нет. Вызывать из обработчика клавиши, пока событие доставляется. Фильтр приложения нужен потому, что `KeyEvent` в QML не отдаёт `nativeVirtualKey`, а на macOS физическая клавиша только в нём: синглтон при создании ставит фильтр событий приложения, и тот запоминает ключ, модификаторы и нативные коды последнего нажатия или отпускания. Коды берутся, если ключ и модификаторы запомненного события равны ключу и модификаторам `KeyEvent`, иначе метод возвращает `event.key`. Окно создаёт `Roost` при старте (`singletonInstance` в `main.cpp` до загрузки QML), чтобы фильтр стоял до первой клавиши: синглтон, созданный первым обработчиком клавиши, пропустил бы то нажатие.
- `Roost.connected` — только чтение, `true` пока окно соединено с `roostd`.
- `Roost.theme` — только чтение, цвета окна и панелей по ролям (`src/qml_api/theme.hpp`); свойство синглтона, потому что встроенные плагины ходят через публичный API (ADR 009). Токен — роль, а не место: QML берёт `Roost.theme.textSecondary`, а не литерал. Любой токен — `color`, кроме `categories`: список из восьми цветов, индекс — `colorIndex` модели. Один сигнал `Roost.theme.changed` на любое изменение (привязки перечитываются сами). Тема по умолчанию — ресурс `src/core/themes/default.json`, светлая (18-style.md). Тему выбирает `settings.theme` (id темы): окно следит за документом `settings` (`Theme::follow`), `roostd` читает его при старте и после каждой записи (§ «Цвета» в 03-terminal.md). Встроенная тема одна, `default`; неизвестный id или не строка — `default` и предупреждение в лог. Для тестов id `test` берёт токены из файла, названного переменной окружения `ROOST_TEST_THEME_FILE` (его читают и окно, и `roostd`); без переменной `test` — неизвестный id. Токены терминала не свойства QML: их берёт C++ (`Theme::terminalColors()`). Шрифты — тоже свойства темы, но берутся из `settings`, а не из темы: `Roost.theme.terminalFont` (шрифт терминалов) и `Roost.theme.uiFont` (шрифт окна), оба `font`. `Theme::follow` читает `settings.terminalFont {family, size}` и `settings.uiFontSize` (`ResolveFontSettings`, `src/core/theme_source.hpp`, один разбор для всех окон). Без ключей — вид сегодняшний: системный моноширинный шрифт терминала (`DefaultTerminalFont()`) его размера и шрифт приложения по умолчанию для окна. Размер — число пунктов от 6 до 72 (`MIN_FONT_SIZE`, `MAX_FONT_SIZE`); не число, меньше 6 или больше 72 — размер по умолчанию. Семейство, которого нет в системе или которое не моноширинное, — системный моноширинный шрифт; общее имя `monospace` (любой регистр) и есть системный моноширинный шрифт, без проблемы (`QFontDatabase` такого семейства не знает). Каждая неверная настройка — одна запись `{setting, text}` в `Roost.theme.settingsProblems` (`setting` — ключ документа `settings`: `terminalFont`, `uiFontSize`, `focusColor`; `text` — причина), а окно показывает `text` в полосе проблем и под полем настройки в окне настроек: `settings.terminalFont.family "X" is not an installed monospace font; the system monospace font is used`, `settings.terminalFont.family must be a font family name; the system monospace font is used` (не строка или пустая), `settings.terminalFont must be an object with family and size; the defaults are used`, `settings.terminalFont.size must be a number from 6 to 72; the default size is used` и `settings.uiFontSize must be a number from 6 to 72; the default size is used`; исправил настройку — строка уходит. Токен `focus` — единственный, который меняет настройка: `settings.focusColor {preset, custom}` (`ResolveFocusSettings`, `src/core/theme_source.hpp`, один разбор для всех окон). `preset` — `base` (`focus` самой темы, `#225fc2`; без ключа то же), `contrast` (`#1b2430`) или `custom` (цвет — `custom`, `#rrggbb`). Любой `#rrggbb` в `custom`, как и любой из двух пресетов, применяется как токен `focus` во всех окнах и после перезапуска; состояния «отказано, прежний цвет» нет. Контраст — предупреждение, а не отказ: применённый цвет проверяется на текущей теме по одной таблице пар (`FOCUS_PAIRS`, `src/qml_api/theme.cpp`; `Contrast` из `src/core/terminal_theme.hpp`, как WCAG; пары и пороги те же, что `TheDefaultThemeHasTheContrastOfTheStyleGuide` в `theme_test`): `surface` 4.5, `canvas` 3, `cursorFocused` 3, `selectedBackground` 4.5. Если пара ниже порога, в `Roost.theme.settingsProblems` встаёт одна запись `setting: focusColor` про худшую пару (с наименьшим отношением контраста к порогу), например `focus colour #f0f0f0 is 1.0:1 on selectedBackground, below 4.5:1` (контраст отсечён до десятых, не округлён). Запись пересчитывается при каждой смене темы и настроек; Base и Contrast на теме по умолчанию её не вызывают. Отказывается только то, что не цвет: `custom` не вида `#rrggbb` (`blue`, `#12g`, пустая строка), `custom` нет при `preset: custom`, неизвестный `preset`, ключ не объектом. Тогда токен — `focus` самой темы (Base), а запись `setting: focusColor` называет причину, например `settings.focusColor.preset must be base, contrast or custom; the focus colour of the theme is used`. Исправил настройку — строка уходит. Смена шрифта и цвета фокуса действует во всех окнах сразу (`store.changed`); у открытого терминала пересчитываются ячейка и сетка, новый размер уходит в PTY (`session.resize`). Окно (`Main.qml`) — `ApplicationWindow` с `font: Roost.theme.uiFont`: шрифт наследуют Controls и `Label` под ним, панели плагинов в том числе. Простой `Text` шрифт родителя не наследует, поэтому в панелях вместо него `Label`; `TextInput` берёт `font` у соседнего `Label`, `TextEdit` — у `root.font` диалога. Шаблон плагина (`templates/plugin-qml`) тоже на `Label`. Терминальная панель привязывает `font: Roost.theme.terminalFont`. Размер шрифта терминала меняют и клавиши, не только окно настроек: команды плагина `terminal` `terminal.fontBigger` (`Cmd+=` и `Cmd+Shift+=`, на Linux `Ctrl+Shift+=`), `terminal.fontSmaller` (`Cmd+-` и `Cmd+Shift+-`, на Linux `Ctrl+Shift+-`) и `terminal.fontDefault` (`Cmd+0`, `Ctrl+Shift+0`; на Linux с Shift, чтобы `Ctrl+=`, `Ctrl+-` и `Ctrl+0` доходили до программы в терминале). Обработчики ставит окно (`Main.qml`, см. §16), и размер один на все окна и панели, а не на панель: первые две пишут `{terminalFont: {size}}` одним `store.patch` того же документа и пути, что поле размера в окне настроек, на 1 больше или меньше текущего размера темы (`Roost.theme.terminalFont`, то есть по умолчанию, когда ключа нет); пока запись не дошла до темы, окно считает текущим размер, который записало последним, поэтому две клавиши подряд дают +2, а не одну и ту же запись дважды; так что все окна следуют через `store.changed`, размер переживает перезапуск, а поле «Terminal font size» показывает новое значение. Пределы те же, 6 и 72 (`MIN_FONT_SIZE`, `MAX_FONT_SIZE`); на пределе команда ничего не пишет, а полоса проблем говорит почему: `Terminal font size is already at the maximum (72)` или `Terminal font size is already at the minimum (6)`; строка уходит, когда размер стал другим (следующей клавишей, из окна настроек, из другого окна), и сама не возвращается, если размер потом вернулся к прежнему. Если запись не удалась, в полосе `Terminal font size was not saved: <причина>`, а если не удалось прочитать документ для `terminal.fontDefault` — `Terminal font size was not reset: <причина>`. `terminal.fontDefault` удаляет `size` из `terminalFont` (как пустое поле) и объект вместе с ним, если `size` был его последним ключом; без сохранённого `size` ничего не пишет. В QML окна и плагинов (`src/roost/**`, все `.qml` в `plugins/<id>/`, `templates/plugin-qml/**`) значением цветового свойства (имя оканчивается сегментом с `color`: `color`, `border.color`, `fillColor`; `palette.<роль>`; объявление `property color <имя>`; привязка `имя: значение` или присваивание `x.color = значение`) не бывает литерал цвета (`"#rrggbb"`, `"#aarrggbb"`) и имя цвета (кроме `"transparent"`); вызовов `Qt.rgba` и подобных нет нигде. Строка `text: "Orange"` или `text: "#123"` не цвет; это держит `tools/check_qml_colors.sh` (CI, задача `gates`), фикстуры — `tests/gates/qml_colors/`.

  Панель лежит в карточке, и карточка не обрезает содержимое: собственный фон или наложение панели на весь размер (справка поверх списка) повторяет угол карточки радиусом `radiusCard` или отступает от края на `cornerInset`, если рисует квадрат (терминал). Терминал вмещает целое число строк и столбцов; остаток меньше ячейки (справа и снизу от сетки) `TerminalItem` закрашивает фоном терминала по умолчанию, а не оставляет карточке (`updatePaintNode`, первый узел под сеткой), поэтому у темы с тёмным `terminalBackground` полоса не светится цветом `surface`. Промежуток между карточками (ручка сплита, `panelGap`) ничего не рисует: в нём виден холст окна, `canvas`.

Роли `Roost.sessions` — поля строки `sessions.list`, фиксированный список `api::SessionService::FIELDS`: `agent`, `id`, `title`, `cwd`, `state`, `startedAt`. Поле, которого в строке нет (`startedAt` бывает не у всех), читается как `undefined`. Новое поле строки `sessions.list` добавляют в `FIELDS`, иначе QML его не увидит. В делегате роль читают как `model.<имя>`. Для двух ролей это обязательно: `required property string id` не допускается, `id` в QML зарезервировано; голое `state` в делегате — свойство `Item.state`, а не роль, и даёт пустую строку. Строку по ключу `(agent, id)` плагин находит перебором: `Roost.sessions.data(Roost.sessions.index(i, 0), Qt.UserRole + n)`, где `n` — позиция поля в `FIELDS` (`agent` — 0, `id` — 1); поиска по ключу у модели нет.

`Api` живёт в GUI-потоке; сокет и разбор кадров — в IO-потоке (`IoThread`). События идут в GUI-поток через очередь в порядке прихода. Ответ завершает свой `QFuture` в IO-потоке. Продолжение `.then(context, …)`, повешенное до ответа, встаёт в ту же очередь за событиями, пришедшими раньше ответа. Продолжение, повешенное на уже готовый future, выполняется сразу и обгоняет такие события, если они ещё в очереди. Колбэки QML (`Roost.*`) всегда идут через очередь (`answerLater`, `src/qml_api/js_callback.cpp`), поэтому видят все события, пришедшие до ответа. C++, которому нужно состояние после своей записи, ждёт событие (например, документ в `StoreService::Cached`), а не ответ на запись. Сервисы-кеши (`PluginService`, `SessionService`, `StoreService`) держат копию состояния roostd и обновляются событиями шины; пока соединения нет, кеши сессий и документов пусты, список плагинов остаётся прежним до следующего ответа. Потерянное соединение и неудачную попытку `Api` повторяет на том же сокете без конца: пауза 0,5 с, после каждой неудачи удваивается до 30 с, успешный hello возвращает 0,5 с (значения задаются `ApiOptions`). `Disconnected` приходит один раз на потерю живого соединения или на неудачу первой попытки, дальнейшие неудачи молчат. Вызовы, висевшие в момент потери, завершаются `ConnectionLost` (-32002) и не повторяются: `commands.run` и `store.set` не идемпотентны. После hello `BusService` заново подписывает все шаблоны, у которых остались слушатели, под прежними локальными id; подписка, сделанная без соединения, уходит на ближайшем hello. Затем кеши запрашиваются заново, и только потом приходит `Connected`. Пока ответ `sessions.list` содержит непустой `unavailable` (или списка ещё не было), `SessionService` просит список заново: пауза 0,5 с, после каждого такого ответа удваивается до 30 с (значения `FirstRelistDelay` и `MaxRelistDelay` в `ApiOptions`). Число повторов не ограничено, пока соединение живо. Ответ с пустым `unavailable` останавливает повторы и возвращает паузу 0,5 с. Повтор один за раз, любой `Refresh` его отменяет и решает ответ последнего; при потере соединения таймер останавливается. Каждый сервис держит ровно одну подписку: при потере он её снимает, при `Start` ставит снова. Ответ hello с ошибкой, кроме `ConnectionLost` (например, `VersionMismatch`), останавливает повторы и даёт `Refused`; новый вызов `Api::Connect` начинает попытки заново. Каналы сессий терминала при потере теряются. `WarmTerminals` (`src/terminal/warm_terminals.hpp`, им владеет `Api`) убирает скрытые терминалы, показанной сессии ставит статус `disconnected` с последним экраном и по `Connected` открывает заново только её (`opening`, затем `open`); `TerminalItem` и `SessionPane` (`src/terminal/session_pane.hpp`) ничего не переоткрывают сами.

Версии SDK:

- Semver SDK не зависит от версии roost и от `api` манифеста; теги `sdk-v*`.
- 0.x: заголовки требуют `ROOST_SDK_UNSTABLE_API`, minor совпадает точно. Обещано только рукопожатие: `roost_plugin_query` и первые четыре поля `roost_plugin_info` не меняются, несовместимый плагин отвергается с сообщением, а не падает.
- 1.0 — когда на SDK работают 2–3 настоящих плагина, из них хотя бы один сторонний, каталог методов не менялся релиз и проверки ABI в CI зелёные. Тот же критерий снимает пометку нестабильности с API `0` манифеста.

Падения нативного плагина — ответственность его автора: код работает в процессе окна без изоляции (§12).
