# 5. Плагины

Плагин — каталог:

```
plugins/claude/
  plugin.json
  qml/            # UI: панели, страницы настроек (необязательно)
  backend/        # любой исполняемый файл с JSON-RPC по stdio (необязательно)
  lib/            # нативная библиотека на SDK (необязательно)
```

`plugin.json`:

```json
{
  "id": "claude",
  "version": "0.1.0",
  "api": "0",
  "backend": { "command": ["backend/claude-adapter"] },
  "contributes": {
    "agents": [{ "id": "claude", "capabilities": ["backgroundDaemon", "nativeTuiAttach"] }],
    "panels": [{ "id": "transcript", "qml": "qml/Transcript.qml",
                 "inputs": { "session": "SessionRef" }, "outputs": {} }],
    "commands": [{ "id": "claude.newSession", "title": "New Claude session" },
                 { "id": "claude.stop", "title": "Stop Claude session" },
                 { "id": "claude.remove", "title": "Remove Claude session" },
                 { "id": "claude.respawn", "title": "Respawn Claude session" },
                 { "id": "claude.respawnAll", "title": "Respawn all Claude sessions" }],
    "keybindings": [{ "command": "claude.newSession", "key": "Ctrl+Alt+N", "mac": "Cmd+Alt+N" }],
    "settings": "qml/Settings.qml"
  }
}
```

| Часть | Как работает | Где выполняется |
|---|---|---|
| UI | QML с диска через `QQmlComponent`, без шага компиляции; в режиме разработки перезагружается при изменении файла | GUI-поток окна, рендер — поток рендера |
| API для QML | один QML-синглтон `Roost` (модуль `Roost.Api`) со свойствами `commands`, `store`, `bus`, `connected` и методами `call` и `bindingKey`; `TerminalItem` — зарегистрированный QML-тип: свойство `session` (`SessionRef` или `null`) показывает сессию через тёплые терминалы окна (`api::Api::Terminals()`): тёплая сессия показывается сразу, остальные открываются через `session.open`; смена сессии или `null` канал не закрывает, `status` (`none`, `opening`, `open`, `ended`, `failed`, `disconnected`) и `statusMessage` говорят, как идут дела, `reopen()` открывает кончившуюся, отказавшую или потерянную сессию заново | GUI-поток |
| Лёгкая логика | JavaScript в QML | GUI-поток |
| Тяжёлая логика и состояние | бэкенд-процесс плагина, любой язык | отдельный процесс, запускает `roostd` |
| Нативный код | библиотека на SDK с C ABI; свои QML-типы на C++ — QML-модуль плагина (ниже) | GUI-поток окна и потоки самого плагина |

- Встроенные фичи живут в `plugins/` и ходят через тот же API: список сессий с категориями, пинами, архивом и непрочитанными; терминальная панель; команды самого окна (плагин `shell`: манифест без панелей и бэкенда, §16); уведомления; PR по worktree; keep-awake; адаптер Claude. Заменить фичу — выключить встроенный плагин и поставить другой с теми же вкладами. Выключает ключ `plugins.disabled` документа `settings` (08-state.md): список id плагинов, например `{"plugins": {"disabled": ["sessions"]}}`. `roostd` пропускает при загрузке плагины с этими id, встроенные и пользователя, и это не проблема: id пропущенных установленных плагинов (по одному, в порядке загрузки) `roostd` отдаёт в `disabled` ответа `plugins.list`, и окно называет такой плагин в заглушке его панели (06-panels.md); id, которого нет среди установленных, ничего не делает. Список читается один раз при старте `roostd` (перечитывания плагинов в демоне нет), поэтому правка действует после его перезапуска. Значение, которое не массив строк (или `plugins`, который не объект, или нечитаемый `settings.json`), — проблема в `problems` ответа `plugins.list` и в логе `roostd`, и ничего не выключено. Окно выбирает список и терминал раскладки по умолчанию по их портам (06-panels.md), так что замена списка — каталог плагина с панелью, у которой выход `selected` типа `SessionRef`, плюс этот ключ, без правок кода. Переключателя в окне настроек нет.
- Конфликт вкладов (две команды с одним id, два хоткея на одну клавишу) решается порядком загрузки плюс явным переопределением пользователя в `keymap.json` (§16); конфликт виден в палитре команд (§16, «Палитра»).
- API версии `0` нестабилен до SDK 1.0 (критерий — в «Версии SDK» ниже).
- Разовый вызов из QML (`Roost.call`, `commands.run`, `commands.registerCommand`, `store.get`, `store.set` и `store.patch`, `keymap.get`, `bus.publish`, `sessions.refresh`) принадлежит панели, в чьём QML-контексте определена вызывающая функция; помощник на JS, определённый в оболочке или в файле `.pragma library`, принадлежит окну. Окно регистрирует контекст каждой панели при её создании (`PluginLoader`, `src/roost/plugin_loader.hpp`). После выгрузки колбэки вызовов панели не вызываются независимо от порядка выгрузки, а вызов из выгружаемой панели отбрасывается и в `roostd` не уходит. Сигналы так не обрываются: при выгрузке отключаются `Connections` и `Roost.store.changed.connect(объект, функция)`, а `Roost.store.changed.connect(функция)` живёт до явного `disconnect`.
- `id` панели в манифесте — имя внутри плагина: непустое, из строчных латинских букв, цифр, `_` и `-` (как id плагина, но без `.`). Окно строит полный id типа панели как `<id плагина>.<имя>`: `list` в плагине `sessions` — панель `sessions.list`; полный id используют слоты окна, связи и `CreatePanel`. Имя с точкой или другим недопустимым символом — проблема загрузчика (панель не создаётся, остальные панели плагина грузятся). Имя без точки, а id плагина уникален, поэтому панели разных плагинов не пересекаются: `a.b` с именем `c` и `a` с именем `b.c` дали бы один тип `a.b.c`, и второе имя отвергается.
- QML-панели (`contributes.panels`) грузит окно (`PluginLoader`): у плагина один контекст QML, у типа панели один `QQmlComponent` из файла `qml`, у каждого экземпляра свой контекст. Корень панели — `Item`; необязательные свойства `pluginId` и `instanceId` получают id плагина и id панели в раскладке окна (`CreatePanel(panelId, instanceId)`; у слотов фиксированной раскладки это `list` и `terminal`) до `Component.onCompleted`. Входы и выходы панели — обычные свойства; каждый заявленный в манифесте вход и выход должен быть свойством корня, иначе это проблема загрузчика (панель всё равно создаётся); `SessionRef` — `{agent, id}` или `null`. Манифест панелей проверяет само окно, `roostd` проверяет только, что `panels` — массив: запись — объект, `id` — имя панели (правило выше), `qml` — непустая строка, путь внутри каталога плагина (по тексту, как путь бэкенда), `inputs` и `outputs`, если есть, — объекты, файл существует и компилируется, имя не повторяется в плагине (вторая панель с тем же именем — проблема), корень — `Item`. Сломанная панель отключает только себя: причина идёт в лог окна и в список проблем загрузчика, а не в `plugins.list`. Изменённый плагин (каталог, версия или `contributes`) выгружается и грузится заново вместе с панелями. Если после выгрузки чего-либо загружается плагин, кеш компонентов сбрасывается (один раз за список), чтобы правки QML читались с диска; компоненты оставшихся плагинов Qt в кеше сохраняет. Неизменённый плагин не трогается, его панели остаются. Экземпляр разбирается в таком порядке: сигнал `PanelAboutToBeDestroyed` (панель ещё жива), владелец вызовов, корень, контекст; через `deleteLater` не удаляется, корень снаружи не удаляют (только `DestroyPanel`), окно не разбирает панель изнутри её JS-вызова или обработчика события; у выгружаемого плагина `CreatePanel` ничего не отдаёт, в том числе из слота `PanelAboutToBeDestroyed`. Ждущие вызовы разобранной панели не отвечают никогда.
- Окно настроек (`src/roost/SettingsWindow.qml`; страницы плагинов ему отдаёт `roost::SettingsPages`, `src/roost/settings_pages.hpp`): одно окно верхнего уровня, `Main.qml` создаёт его один раз; закрытие его прячет, повторное открытие поднимает то же окно. Открывает его команда `shell.settings` (§16): `Cmd+,` и пункт «Settings…» меню на macOS, кнопка «Settings…» панели инструментов на Linux. Меню на macOS — родное: у `MenuItem` Qt Quick Controls роли нет, а Cocoa-плагин Qt по тексту пункта («Setting», «Preferences», «Options», «Setup», «Config») считает его настройками приложения и переносит в меню приложения (строки есть в `libqcocoa`; на живом окне не проверено). Qt обнуляет высоту родного `MenuBar` (`QQuickMenuBarPrivate::createNativeMenuBar`), но неявную оставляет, поэтому строка `menuBarLoader` в `Main.qml` берёт высоту из `item.height`: родное меню места в окне не занимает, а в offscreen-тестах меню остаётся в окне над баннером (высоту родного меню на живом окне не проверяли).
  - Общий раздел (A17) — документ `settings` (§8): тема (id, которые знает окно; сейчас `default`), семейство и размер шрифта терминала, размер шрифта окна, цвет кольца фокуса (`settings.focusColor`, ниже), переключатель «Check for updates» (`settings.updates.check`, §17). Правка поля — один `store.patch` одного ключа (`{uiFontSize: 14}`, `{terminalFont: {size: 15}}`, `{updates: {check: false}}`), правки разных ключей из двух окон остаются обе; пустое поле удаляет ключ (значение по умолчанию), последний ключ `terminalFont` уносит и сам объект (`terminalFont: null`, а не `{}`); текст, не являющийся числом в поле размера, правкой не считается, поле возвращается к значению; так же поле возвращается к хранимому значению, когда запись не удалась, а причина остаётся под полями. Документ и таблица клавиш читаются при первом показе окна; пока `roostd` не подключён или чтение не удалось, под полями причина, и чтение повторяется при каждом подключении. Цвет кольца фокуса — «Focus ring color»: список Base, Contrast, Custom и, только при Custom, поле `#rrggbb` (выбора цвета диалогом в проекте нет); выбор пишет `{focusColor: {preset}}`, а Custom без сохранённого цвета ещё и `custom` с цветом, который кольцо имеет сейчас; поле пишет то, что набрано, одним ключом `custom` (пустое поле удаляет его, последний ключ уносит объект). Проблемы настроек, которые читает тема (`Roost.theme.settingsProblems`), показаны под полем своей настройки: ключ `terminalFont` — под полями шрифта терминала, `uiFontSize` — под полем размера окна, `focusColor` — под строкой «Focus ring color». Списка выключенных плагинов в разделе нет: ключ `plugins.disabled` (выше, «Встроенные фичи…») правится в `settings.json` вручную и действует после перезапуска `roostd`; страницы есть только у загруженных плагинов.
  - Страница плагина — QML-файл `contributes.settings` внутри каталога плагина; у плагина одна страница, без ключа нет и раздела. Корень — `Item`: `implicitHeight` задаёт высоту раздела, свойство `pluginId` получает id плагина до `Component.onCompleted` (как у панели). Страницы создаются при первом показе окна настроек, а не при старте окна: код страницы (`Component.onCompleted`) не работает, пока окно ни разу не открыли. Окно показывает страницу под заголовком с id плагина. `PluginLoader::CreateSettingsPage(pluginId)` стоит рядом с `CreatePanel`: тот же контекст плагина, тот же владелец вызовов, файл разбирается так же. Страница, которая не собирается или чей корень не `Item`, — проблема загрузчика с именем панели `(settings)`, остальное грузится. Созданная страница живёт, пока загружен плагин (закрытие окна её не уничтожает), и уничтожается с плагином (`PanelAboutToBeDestroyed`), через `DestroyPanel` и при выходе; плагин, загруженный заново (diff или `Reload`), получает новую; сигнал `SettingsPagesChanged` говорит об этом. Значения страница хранит в документе своего плагина под ключом `settings` и пишет патчем: `Roost.store.patch(pluginId, {settings: {note: "…"}})`.
  - Хоткеи окно показывает только для чтения (команда, клавиша, источник: из `keymap.get` и `keymap.changed`); кнопка «Open keymap.json» отдаёт файл системе (`Qt.openUrlExternally`), само окно `keymap.json` не пишет (§16).
- Режим разработки, `roost --dev` (только в окне с плагинами, не с `--session`): `PluginWatcher` (`src/roost/plugin_watcher.hpp`) следит за каждым `*.qml`, `*.js` и `qmldir` под каталогом загруженного плагина, за самими каталогами и за родителем каталога плагина (не рекурсивно; плагин с пустым или относительным каталогом пропускается) (`QFileSystemWatcher`; рецепт тот же, что у keymap, §16: событие каталога возвращает под слежение файл, замещённый через `rename`, и подхватывает новые файлы). Через 100 мс после последнего события плагина вызывается `PluginLoader::Reload(id)`: перезагружается только этот плагин, разбор как у изменённого (экземпляры панелей с `PanelAboutToBeDestroyed`, компоненты, контекст, проблемы плагина), кеш компонентов сбрасывается, плагин грузится заново с тем же объявлением; ждущие вызовы его панелей не отвечают. Событие, после которого время изменения, размер и время смены прав пути те же (чтение файла самим перезагрузчиком), перезагрузку не запускает. Удалённый файл — одна перезагрузка (панель, которой он нужен, становится проблемой загрузчика), записанный снова — ещё одна. Удалённый каталог плагина — одна перезагрузка (все его панели становятся проблемами); когда каталог создан снова, даже спустя время, событие родителя запускает перезагрузку, и плагин возвращается. Всего отслеживается не больше 256 путей (каталоги, в том числе родители, первыми); что не поместилось, перечислено в `qWarning` один раз на набор, остальное работает. Теряется оконное состояние панелей плагина (выбор в списке и т. п.); что панель держит в `Roost.store` или в `roostd`, возвращается. Манифест и нативные библиотеки не перечитываются: `roostd` читает `plugin.json` при старте, поэтому правка манифеста требует перезапуска `roostd`; окно переподключится, и загрузчик перезагрузит изменённый плагин как обычно. `Reload` нельзя вызывать из JS-вызова панели: вызывает его таймер.
- Сборка раскладывает встроенные плагины в `build/<пресет>/roost-plugins/<id>/`: `plugin.json`, `qml/` (если есть; в нём `qml/<URI>/` с собранным QML-модулем на C++, если он есть) и `backend/` (если есть). Демон находит их сам: `build/<пресет>/bin/roostd` ищет `../roost-plugins`, переменная не нужна. Это копии: CMake копирует `plugin.json` и файлы QML при конфигурации, поэтому `roost --dev` следит за копией в `build/<пресет>/roost-plugins`, а не за файлами в `plugins/`. Правка `plugins/<id>/qml/*.qml` доходит до окна после `cmake --build --preset dev`.
- Поиск: каталоги из `ROOST_PLUGINS_PATH` (через `:`, только абсолютные пути), а если переменная не задана, пуста или в ней нет ни одного абсолютного пути — встроенный каталог пакета; затем `<каталог состояния>/plugins`; каталог, названный дважды, просматривается один раз. В каждом — подкаталоги с `plugin.json`, по имени с учётом регистра: заглавные раньше строчных. Порядок поиска и есть порядок загрузки. Встроенный каталог (`BundledPluginsDirectory`, `src/roostd/manifest.cpp`) — первый существующий из трёх путей от каталога бинарника `roostd`, в этом порядке; нет ни одного — его нет в поиске. Пути: `<каталог roostd>/../Resources/roost-plugins` — в `roost.app` это `Contents/Resources/roost-plugins` (`roostd` лежит в `Contents/MacOS`); `../lib/roost/plugins` — в AppImage `usr/lib/roost/plugins` внутри монтирования образа (`roostd` — `usr/bin/roostd`, его запускает `$APPIMAGE --roostd`, §11), так же в установленном `usr/` (`cmake --install`, Linux); `../roost-plugins` — в дереве сборки `build/<пресет>/roost-plugins` (`build/<пресет>/bin/roostd`). Код плагина (бэкенд `claude-adapter`, библиотека QML-модуля) лежит в тех же каталогах плагинов; в `.app` это симлинки на `Contents/MacOS` и `Contents/PlugIns/roost`. Заданная переменная заменяет встроенный каталог: чтобы сохранить встроенные плагины, перечисли его в ней. Второй плагин с тем же `id` не загружается: плагин пользователя с `id` встроенного проигрывает ему, причина — в `problems` ответа `plugins.list`; чтобы поставить свой плагин на место встроенного, встроенный выключают (`plugins.disabled`, выше), а свой ставят под другим `id`: `plugins.disabled` пропускает все плагины с этим `id`, и плагин с `id` встроенного выключился бы вместе с ним.
- Заготовка плагина с QML-панелью — `templates/plugin-qml/` (README с шагами и с добавлением бэкенда, на русском и английском); сборка её не трогает.
- Манифест проверяется при загрузке (`src/roostd/manifest.hpp`): `api` совпадает с API демона, программа бэкенда и `settings` — пути внутри каталога плагина (проверка по тексту пути, симлинки не раскрываются: код плагина и так работает от имени пользователя), хоткей назначен на команду того же плагина, у плагина с агентами есть бэкенд. Id агента — как id плагина; агент, объявленный вторым плагином, остаётся за первым. Хоткей команды, проигравшей конфликт, тоже не действует. Неизвестные ключи игнорируются. Плагин с битым манифестом не загружается, а остальные загружаются; отказ и каждый проигравший конфликт сохраняются как проблема для пользователя.
- Бэкенд (`src/roostd/backend.hpp`) запускается в каталоге плагина, в своей сессии: Ctrl-C в терминале демона до него не доходит. Протокол — JSON-RPC 2.0, одно компактное сообщение на строку в stdin и stdout; stderr бэкенда идёт в stderr демона. Демон шлёт запросы и ждёт ответов без таймаута; уведомления бэкенда принимает, а на запрос от бэкенда пока отвечает `MethodNotFound`. Закрытый stdin значит «завершись»: через секунду после этого процесс убивается.
- Бэкенд упал, если сам завершился, не запустился или нарушил протокол: строка не JSON-RPC, ответ на чужой id, ответ без `result` и `error`, `error` не объектом, строка длиннее 16 МиБ. Нарушителя демон убивает. Ждущие запросы получают -32003, демон перезапускает бэкенд через 0,5 с, и с каждым падением подряд пауза удваивается, до 30 с. После пятого перезапуска подряд бэкенд остаётся лежать. Минута работы без падений обнуляет счёт.

Цена: JavaScript плагина выполняется в GUI-потоке, и небрежный плагин может подвесить окно. Смягчение — бэкенд-процессы для тяжёлого и оверлей времени кадра в режиме разработки, который называет медленную панель.

## Нативные плагины

Два уровня с разными гарантиями:

| Уровень | Что даёт | Чья гарантия совместимости |
|---|---|---|
| C ABI (`roost/plugin.h`) | вызовы API roost, шина, хранилище, команды | roost: тот же major SDK, minor не выше, чем у roost; в 0.x minor совпадает |
| QML-модуль на C++ | свои QML-типы, модели, `QQuickItem` | Qt: та же major-версия, minor не выше, чем у Qt в roost |

Через C ABI не ходят типы Qt и классы C++. Свои QML-типы плагин отдаёт стандартным QML-модулем (`qt_add_qml_module`), а с roost такой модуль говорит только через `Roost.*`, без заголовков roost.

Qt 6 совместим назад внутри major-версии: «Minor releases are backwards binary and source compatible» (https://wiki.qt.io/Qt-Version-Compatibility). Плагин, собранный с более новым Qt или в другом режиме (debug или release), Qt не загружает (https://doc.qt.io/qt-6/deployment-plugins.html). Отсюда правила для QML-модуля плагина:

- собирать в release против Qt 6.8 — нижней границы, с которой собирается сам roost (`find_package(Qt6 6.8 ...)` в `CMakeLists.txt`); такой модуль грузится в roost на любом Qt 6.8 и новее внутри Qt 6;
- пользоваться только публичным API Qt: приватные заголовки (`QQuickItemPrivate`, внутренности scene graph) гарантией совместимости не покрыты;
- свою копию Qt не класть: модуль использует Qt из бандла roost. Что вторая копия при этом не появляется, проверяется в M9 (§14).

Манифест:

```json
"native": { "library": "lib/libfoo", "sdk": "0.1", "qt": "6.8", "qmlImportPath": "qml" }
```

| Ключ | Когда нужен | Что значит |
|---|---|---|
| `library` | есть библиотека на C ABI | путь без расширения, roost добавляет `.dylib` или `.so` |
| `sdk` | вместе с `library` | версия SDK, с которой собрана библиотека |
| `qt` | библиотека или QML-модуль линкуют Qt | версия Qt, с которой они собраны |
| `qmlImportPath` | есть QML-модуль | каталог, который окно добавляет в import path движка |

Пути `library` и `qmlImportPath` проверяются, как путь бэкенда: внутри каталога плагина, по тексту пути.

QML-модуль плагина, без библиотеки на C ABI:

- Работают `qt` и `qmlImportPath`. `qt` — `"MAJOR.MINOR"` без патча, такой же major, как у Qt в roost, и minor не выше. Оба ключа необязательны. `library` и `sdk` пока отказывают весь плагин с причиной в проблемах (до SDK 0.1, M9).
- `roostd` отдаёт `native` в `plugins.list`, только если плагин его объявил; окно не различает отсутствующий ключ и пустой объект: в обоих случаях добавлять нечего. Окно добавляет `<каталог плагина>/<qmlImportPath>` в import path движка после путей, которые там уже были: плагин не подменяет модуль roost, а модуль с одним URI у двух плагинов принадлежит тому, кто раньше в порядке загрузки. Пути стоят до загрузки панелей, поэтому панель делает `import <URI>`.
- Изменение `native` перезагружает плагин, как изменение `contributes`; выгруженный плагин убирает свой каталог из import path. Модуль, который движок уже импортировал, остаётся в нём до выхода: библиотеку модуля Qt держит загруженной, изменённую подхватывает перезапуск окна.
- Рецепт для модуля на чистом QML: `native: {"qmlImportPath": "qml"}`, в `qml/<URI, точки как каталоги>/` лежат `qmldir` (`module <URI>`, строка `Тип 1.0 Тип.qml` на тип) и файлы типов, панель начинается с `import <URI>`. URI не из пространства `Roost.*`: оно у roost.
- Рецепт для модуля на C++ в дереве roost (`plugins/sessions/`): `qt_add_plugin(<цель> CLASS_NAME <URI без точек>Plugin)`, затем `qt_add_qml_module(<цель> PLUGIN_TARGET <цель> URI <URI> VERSION 1.0 OUTPUT_DIRECTORY ${ROOST_<ID>_PLUGIN_DIR}/qml/<URI, точки как каталоги> NO_CACHEGEN SOURCES ...)`. Без `qt_add_plugin` Qt собирает отдельные библиотеку и плагин, и каталог модуля не самодостаточен. Логика лежит в статической библиотеке с `POSITION_INDEPENDENT_CODE ON`, которую линкует модуль и тесты; на ней `qt_extract_metatypes`. Тип из библиотеки регистрируется обёрткой `struct { Q_GADGET QML_FOREIGN(Тип) QML_NAMED_ELEMENT(Имя) }` в отдельном `module/*.hpp`, на который указывает `target_include_directories` модуля. Манифест: `native: {"qt": "6.8", "qmlImportPath": "qml"}`. Тест загружает модуль через `QQmlEngine::addImportPath(<выходной каталог>/qml)`. Гейт плагинов принимает эту форму: цель линкует только Qt и библиотеку плагина.

Загрузка и рукопожатие:

- Нативный код грузится только в окне, через `QLibrary`. Код на стороне демона — бэкенд-процесс.
- `roostd` проверяет ключ `native` вместе с остальным манифестом: плагин не загружается, если major SDK не совпадает, minor SDK выше, чем у roost (в 0.x — не равен), или Qt другой major-версии либо новее Qt в roost. Отказывает весь плагин: QML, библиотека и бэкенд. Причина попадает в проблемы для пользователя, как битый манифест.
- Макрос `ROOST_PLUGIN(...)` экспортирует три функции и больше ничего: `roost_plugin_query` (статическая `roost_plugin_info {struct_size, sdk_major, sdk_minor, id, qt_version, encoding}`), `roost_plugin_init(const roost_host*, ctx**)` и `roost_plugin_shutdown(ctx)`.
- Окно загружает библиотеку и вызывает `query`. Если ответ расходится с манифестом, окно не вызывает `init` и не грузит QML плагина, причина — в проблемах. Загрузка уже исполняет статические инициализаторы плагина, поэтому несовместимость ловит манифест, а `query` её только подтверждает.
- Закрытие: окно уничтожает QML плагина, отменяет его подписки и ждущие вызовы (после этого колбэки плагина не вызываются), затем вызывает `shutdown`. Библиотека остаётся загруженной до выхода. Перезагрузка QML работает как раньше; изменённую библиотеку подхватывает перезапуск окна, состояние и тёплые сессии при этом в `roostd`.

Как растёт API:

- `roost_host {struct_size, sdk_minor, …}` и таблицы функций, которые плагин передаёт в roost, только дописываются в конец. Обёртка проверяет `struct_size` перед вызовом функции из более новой версии; таблицу плагина roost копирует в обнулённую структуру по меньшему из размеров, по образцу libobs (`obs_register_source_s`, https://github.com/obsproject/obs-studio/blob/7cad8fc22ad3ea68e44d056fde57be2fe0f5b719/libobs/obs-module.c).
- Функции хоста — `call(method, payload, cb, user)`, `subscribe(pattern, cb, user)`, `unsubscribe`, `publish(name, payload)`, `post_to_gui(fn, user)`, `log`. Имена методов и схемы — каталог §4: новый метод API — новое имя, а не новый ABI. Отдельные типизированные функции появляются только для горячих путей и тоже дописываются в конец.
- Кодировка данных объявлена в `roost_plugin_info.encoding`. В 0.x это JSON; бинарный формат (FlatBuffers, protobuf) выбирается в M9 по замеру вызовов в GUI-потоке.
- Несовместимое изменение — `roost_host_v2` рядом с v1; v1 обслуживается до следующего major.

Потоки и память:

| Что | Правило |
|---|---|
| `post_to_gui`, `log` | из любого потока; `post_to_gui` вызывает `fn(user)` в GUI-потоке |
| остальные функции хоста | только из GUI-потока; отладочная сборка падает на нарушении, в релизе поведение не определено |
| колбэки `call` и `subscribe` | приходят в GUI-поток и укладываются в бюджет кадра (§9); тяжёлое — в потоки плагина или в бэкенд |
| данные, которые плагин передаёт в функцию хоста | roost копирует до возврата из функции |
| данные в колбэке | живут до возврата из колбэка; плагин копирует, что ему нужно дольше |

Память через границу не освобождается: каждая сторона освобождает только своё.

Один API: сервисы и диспетчер методов окна лежат в `src/api/`, синглтон `Roost` (`src/qml_api/`) и таблица хоста SDK (`src/sdk_host/`) — адаптеры над ним. Тест сверяет, что каждый метод диспетчера доступен и из `Roost`, и через `host->call`. Роли модели `Roost.sessions` совпадают с полями `sessions.list`.

Контракт `Roost` для QML (`import Roost.Api`). Ответ приходит в колбэк последним аргументом: `callback(error, result)` в GUI-потоке. При успехе `error` — `null`, при отказе `error` — `{code, message, data?}` (коды те же, что в протоколе), а `result` не задан. Колбэк всегда вызывается асинхронно, через цикл событий, и никогда внутри самого вызова. Колбэк `Roost.store.get` обязателен (без него вызов ничего не вернёт), у остальных вызовов его можно опустить: отказ без колбэка попадает в лог предупреждением, исключение из колбэка тоже. Если движок QML уничтожен до ответа, колбэк не вызывается.

- `Roost.call(method, params, callback)`: любой метод диспетчера по имени, как `host->call` в SDK; чего в диспетчере нет (`hello`, `session.open`), то `-32601`.
- `Roost.commands.run(command, args, callback)`.
- `Roost.commands.registerCommand(command, handler)`: даёт команде обработчик в окне, `handler(args)` исполняется при запуске команды (клавишей, палитрой, `run`) без запроса к `roostd`; возвращённое значение — ответ (`undefined` — `null`), исключение — `InternalError`. Возвращает `true`; `false` — пустой id или вызывающая панель выгружается. У команды может быть несколько обработчиков: исполняется последний зарегистрированный из живых. Обработчик живёт, пока жива панель, из чьего контекста вызвана функция (владелец вызовов, правило выше), и снимается при её выгрузке; из QML оболочки — пока живо окно. Не функция вместо обработчика бросает `TypeError`. Имя не `register`: это ключевое слово C++, а moc называет метод так, как он написан. Команду объявляет манифест плагина (`contributes.commands`): там у неё клавиша и место в палитре; `registerCommand` её только исполняет (§16).
- `Roost.sessions` — модель списка сессий всех агентов (`QAbstractListModel`), строки идут в порядке ответа `roostd`, новая сессия добавляется в конец, удалённая (`session.removed`) исчезает из модели как `rowsRemoved`. Свойства: `loaded` (пришёл первый список этого соединения), `unavailable` (массив `{agent, reason}` для агентов, чей адаптер не ответил списком). Сигнал `listed(agent)`: адаптер агента сообщил, что листинг закончен и сессии, которые он изменил, уже переданы (событие `session.listed {agent}`, §7); приходит после загрузки первого списка. `Roost.sessions.refresh(callback?)` запрашивает список заново (`sessions.list`); строки заменяются до вызова колбэка. Пока соединения нет, модель пуста.
- `Roost.store.get(plugin, callback)` отдаёт `{document}`; `Roost.store.set(plugin, document, callback?)`; `Roost.store.patch(plugin, patch, callback?)` сливает `patch` с текущим документом по RFC 7386 (04-protocol.md); сигнал `Roost.store.changed(plugin, document)` приходит для документов, которые уже прочитаны, и при записи из другого окна. Колбэк `get` получает документ таким, каким окно знает его в момент вызова колбэка, если документ уже в кеше окна (прочитан при живой подписке на `store.changed` этого соединения): ответ идёт в колбэк через цикл событий, и `store.changed`, обогнавший его, не откатывается назад старым ответом. Документ не в кеше (до подписки, после разрыва) приходит как ответ `roostd`.
- `Roost.bus.subscribe(pattern, owner, callback)` возвращает id; `callback(name, payload)`. Подписка живёт, пока жив `owner` (объект QML), либо до `Roost.bus.unsubscribe(id)`. `Roost.bus.publish(name, payload, callback?)`.
- Ошибки аргументов `subscribe` (владелец `null`, колбэк не функция, неверный шаблон) бросают `TypeError`; ошибки самих вызовов приходят в колбэк.
- `Roost.bindingKey(event)`: клавиша, которую обработчик `Keys.onPressed` сравнивает с `Qt.Key_*`, на любой раскладке. Принимает `KeyEvent`, возвращает `Qt.Key_*`: `event.key` на латинской раскладке, на нелатинской — клавиша US-раскладки на той же физической позиции (`о` на русской — `Qt.Key_J`, Shift+`б` — `Qt.Key_Less`). Буква приходит заглавной, цифра и символ следуют за Shift. Метод оконный: он ничего не просит у `roostd`, не метод диспетчера и в `host->call` его нет. Вызывать из обработчика клавиши, пока событие доставляется. Фильтр приложения нужен потому, что `KeyEvent` в QML не отдаёт `nativeVirtualKey`, а на macOS физическая клавиша только в нём: синглтон при создании ставит фильтр событий приложения, и тот запоминает ключ, модификаторы и нативные коды последнего нажатия или отпускания. Коды берутся, если ключ и модификаторы запомненного события равны ключу и модификаторам `KeyEvent`, иначе метод возвращает `event.key`. Окно создаёт `Roost` при старте (`singletonInstance` в `main.cpp` до загрузки QML), чтобы фильтр стоял до первой клавиши: синглтон, созданный первым обработчиком клавиши, пропустил бы то нажатие.
- `Roost.connected` — только чтение, `true` пока окно соединено с `roostd`.
- `Roost.theme` — только чтение, цвета окна и панелей по ролям (`src/qml_api/theme.hpp`); свойство синглтона, потому что встроенные плагины ходят через публичный API (ADR 009). Токен — роль, а не место: QML берёт `Roost.theme.textSecondary`, а не литерал. Любой токен — `color`, кроме `categories`: список из восьми цветов, индекс — `colorIndex` модели. Один сигнал `Roost.theme.changed` на любое изменение (привязки перечитываются сами). Тема по умолчанию — ресурс `src/core/themes/default.json`, светлая (18-style.md). Тему выбирает `settings.theme` (id темы): окно следит за документом `settings` (`Theme::follow`), `roostd` читает его при старте и после каждой записи (§ «Цвета» в 03-terminal.md). Встроенная тема одна, `default`; неизвестный id или не строка — `default` и предупреждение в лог. Для тестов id `test` берёт токены из файла, названного переменной окружения `ROOST_TEST_THEME_FILE` (его читают и окно, и `roostd`); без переменной `test` — неизвестный id. Токены терминала не свойства QML: их берёт C++ (`Theme::terminalColors()`). Шрифты — тоже свойства темы, но берутся из `settings`, а не из темы: `Roost.theme.terminalFont` (шрифт терминалов) и `Roost.theme.uiFont` (шрифт окна), оба `font`. `Theme::follow` читает `settings.terminalFont {family, size}` и `settings.uiFontSize` (`ResolveFontSettings`, `src/core/theme_source.hpp`, один разбор для всех окон). Без ключей — вид сегодняшний: системный моноширинный шрифт терминала (`DefaultTerminalFont()`) его размера и шрифт приложения по умолчанию для окна. Размер — число пунктов от 6 до 72 (`MIN_FONT_SIZE`, `MAX_FONT_SIZE`); не число, меньше 6 или больше 72 — размер по умолчанию. Семейство, которого нет в системе или которое не моноширинное, — системный моноширинный шрифт; общее имя `monospace` (любой регистр) и есть системный моноширинный шрифт, без проблемы (`QFontDatabase` такого семейства не знает). Каждая неверная настройка — одна запись `{setting, text}` в `Roost.theme.settingsProblems` (`setting` — ключ документа `settings`: `terminalFont`, `uiFontSize`, `focusColor`; `text` — причина), а окно показывает `text` в полосе проблем и под полем настройки в окне настроек: `settings.terminalFont.family "X" is not an installed monospace font; the system monospace font is used`, `settings.terminalFont.family must be a font family name; the system monospace font is used` (не строка или пустая), `settings.terminalFont must be an object with family and size; the defaults are used`, `settings.terminalFont.size must be a number from 6 to 72; the default size is used` и `settings.uiFontSize must be a number from 6 to 72; the default size is used`; исправил настройку — строка уходит. Токен `focus` — единственный, который меняет настройка: `settings.focusColor {preset, custom}` (`ResolveFocusSettings`, `src/core/theme_source.hpp`, один разбор для всех окон). `preset` — `base` (`focus` самой темы, `#225fc2`; без ключа то же), `contrast` (`#1b2430`) или `custom` (цвет — `custom`, `#rrggbb`). Любой `#rrggbb` в `custom`, как и любой из двух пресетов, применяется как токен `focus` во всех окнах и после перезапуска; состояния «отказано, прежний цвет» нет. Контраст — предупреждение, а не отказ: применённый цвет проверяется на текущей теме по одной таблице пар (`FOCUS_PAIRS`, `src/qml_api/theme.cpp`; `Contrast` из `src/core/terminal_theme.hpp`, как WCAG; пары и пороги те же, что `TheDefaultThemeHasTheContrastOfTheStyleGuide` в `theme_test`): `surface` 4.5, `canvas` 3, `cursorFocused` 3, `selectedBackground` 4.5. Если пара ниже порога, в `Roost.theme.settingsProblems` встаёт одна запись `setting: focusColor` про худшую пару (с наименьшим отношением контраста к порогу), например `focus colour #f0f0f0 is 1.0:1 on selectedBackground, below 4.5:1` (контраст отсечён до десятых, не округлён). Запись пересчитывается при каждой смене темы и настроек; Base и Contrast на теме по умолчанию её не вызывают. Отказывается только то, что не цвет: `custom` не вида `#rrggbb` (`blue`, `#12g`, пустая строка), `custom` нет при `preset: custom`, неизвестный `preset`, ключ не объектом. Тогда токен — `focus` самой темы (Base), а запись `setting: focusColor` называет причину, например `settings.focusColor.preset must be base, contrast or custom; the focus colour of the theme is used`. Исправил настройку — строка уходит. Смена шрифта и цвета фокуса действует во всех окнах сразу (`store.changed`); у открытого терминала пересчитываются ячейка и сетка, новый размер уходит в PTY (`session.resize`). Окно (`Main.qml`) — `ApplicationWindow` с `font: Roost.theme.uiFont`: шрифт наследуют Controls и `Label` под ним, панели плагинов в том числе. Простой `Text` шрифт родителя не наследует, поэтому в панелях вместо него `Label`; `TextInput` берёт `font` у соседнего `Label`, `TextEdit` — у `root.font` диалога. Шаблон плагина (`templates/plugin-qml`) тоже на `Label`. Терминальная панель привязывает `font: Roost.theme.terminalFont`. Размер шрифта терминала меняют и клавиши, не только окно настроек: команды плагина `terminal` `terminal.fontBigger` (`Cmd+=` и `Cmd+Shift+=`, на Linux `Ctrl+Shift+=`), `terminal.fontSmaller` (`Cmd+-`, `Ctrl+Shift+-`) и `terminal.fontDefault` (`Cmd+0`, `Ctrl+Shift+0`; на Linux с Shift, чтобы `Ctrl+=`, `Ctrl+-` и `Ctrl+0` доходили до программы в терминале). Обработчики ставит окно (`Main.qml`, см. §16), и размер один на все окна и панели, а не на панель: первые две пишут `{terminalFont: {size}}` одним `store.patch` того же документа и пути, что поле размера в окне настроек, на 1 больше или меньше текущего размера темы (`Roost.theme.terminalFont`, то есть по умолчанию, когда ключа нет); пока запись не дошла до темы, окно считает текущим размер, который записало последним, поэтому две клавиши подряд дают +2, а не одну и ту же запись дважды; так что все окна следуют через `store.changed`, размер переживает перезапуск, а поле «Terminal font size» показывает новое значение. Пределы те же, 6 и 72 (`MIN_FONT_SIZE`, `MAX_FONT_SIZE`); на пределе команда ничего не пишет, а полоса проблем говорит почему: `Terminal font size is already at the maximum (72)` или `Terminal font size is already at the minimum (6)`; строка уходит, когда размер стал другим (следующей клавишей, из окна настроек, из другого окна), и сама не возвращается, если размер потом вернулся к прежнему. Если запись не удалась, в полосе `Terminal font size was not saved: <причина>`, а если не удалось прочитать документ для `terminal.fontDefault` — `Terminal font size was not reset: <причина>`. `terminal.fontDefault` удаляет `size` из `terminalFont` (как пустое поле) и объект вместе с ним, если `size` был его последним ключом; без сохранённого `size` ничего не пишет.   Панель лежит в карточке, и карточка не обрезает содержимое: собственный фон или наложение панели на весь размер (справка поверх списка) повторяет угол карточки радиусом `radiusCard` или отступает от края на `cornerInset`, если рисует квадрат (терминал). Промежуток между карточками (ручка сплита, `panelGap`) ничего не рисует: в нём виден холст окна, `canvas`.

Роли `Roost.sessions` — поля строки `sessions.list`, фиксированный список `api::SessionService::FIELDS`: `agent`, `id`, `title`, `cwd`, `state`, `startedAt`. Поле, которого в строке нет (`startedAt` бывает не у всех), читается как `undefined`. Новое поле строки `sessions.list` добавляют в `FIELDS`, иначе QML его не увидит. В делегате роль читают как `model.<имя>`. Для двух ролей это обязательно: `required property string id` не допускается, `id` в QML зарезервировано; голое `state` в делегате — свойство `Item.state`, а не роль, и даёт пустую строку. Строку по ключу `(agent, id)` плагин находит перебором: `Roost.sessions.data(Roost.sessions.index(i, 0), Qt.UserRole + n)`, где `n` — позиция поля в `FIELDS` (`agent` — 0, `id` — 1); поиска по ключу у модели нет.

`Api` живёт в GUI-потоке; сокет и разбор кадров — в IO-потоке (`IoThread`). События идут в GUI-поток через очередь в порядке прихода. Ответ завершает свой `QFuture` в IO-потоке. Продолжение `.then(context, …)`, повешенное до ответа, встаёт в ту же очередь за событиями, пришедшими раньше ответа. Продолжение, повешенное на уже готовый future, выполняется сразу и обгоняет такие события, если они ещё в очереди. Колбэки QML (`Roost.*`) всегда идут через очередь (`answerLater`, `src/qml_api/js_callback.cpp`), поэтому видят все события, пришедшие до ответа. C++, которому нужно состояние после своей записи, ждёт событие (например, документ в `StoreService::Cached`), а не ответ на запись. Сервисы-кеши (`PluginService`, `SessionService`, `StoreService`) держат копию состояния roostd и обновляются событиями шины; пока соединения нет, кеши сессий и документов пусты, список плагинов остаётся прежним до следующего ответа. Потерянное соединение и неудачную попытку `Api` повторяет на том же сокете без конца: пауза 0,5 с, после каждой неудачи удваивается до 30 с, успешный hello возвращает 0,5 с (значения задаются `ApiOptions`). `Disconnected` приходит один раз на потерю живого соединения или на неудачу первой попытки, дальнейшие неудачи молчат. Вызовы, висевшие в момент потери, завершаются `ConnectionLost` (-32002) и не повторяются: `commands.run` и `store.set` не идемпотентны. После hello `BusService` заново подписывает все шаблоны, у которых остались слушатели, под прежними локальными id; подписка, сделанная без соединения, уходит на ближайшем hello. Затем кеши запрашиваются заново, и только потом приходит `Connected`. Пока ответ `sessions.list` содержит непустой `unavailable` (или списка ещё не было), `SessionService` просит список заново: пауза 0,5 с, после каждого такого ответа удваивается до 30 с (значения `FirstRelistDelay` и `MaxRelistDelay` в `ApiOptions`). Число повторов не ограничено, пока соединение живо. Ответ с пустым `unavailable` останавливает повторы и возвращает паузу 0,5 с. Повтор один за раз, любой `Refresh` его отменяет и решает ответ последнего; при потере соединения таймер останавливается. Каждый сервис держит ровно одну подписку: при потере он её снимает, при `Start` ставит снова. Ответ hello с ошибкой, кроме `ConnectionLost` (например, `VersionMismatch`), останавливает повторы и даёт `Refused`; новый вызов `Api::Connect` начинает попытки заново. Каналы сессий терминала при потере теряются. `WarmTerminals` (`src/terminal/warm_terminals.hpp`, им владеет `Api`) убирает скрытые терминалы, показанной сессии ставит статус `disconnected` с последним экраном и по `Connected` открывает заново только её (`opening`, затем `open`); `TerminalItem` и `SessionPane` (`src/terminal/session_pane.hpp`) ничего не переоткрывают сами.

Версии SDK:

- Semver SDK не зависит от версии roost и от `api` манифеста; теги `sdk-v*`.
- 0.x: заголовки требуют `ROOST_SDK_UNSTABLE_API`, minor совпадает точно. Обещано только рукопожатие: `roost_plugin_query` и первые четыре поля `roost_plugin_info` не меняются, несовместимый плагин отвергается с сообщением, а не падает.
- 1.0 — когда на SDK работают 2–3 настоящих плагина, из них хотя бы один сторонний, каталог методов не менялся релиз и проверки ABI в CI зелёные. Тот же критерий снимает пометку нестабильности с API `0` манифеста.

Падения нативного плагина — ответственность его автора: код работает в процессе окна без изоляции (§12).
