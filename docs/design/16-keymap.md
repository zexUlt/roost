# 16. Хоткеи

Клавиши назначают два источника: вклады `keybindings` в манифестах плагинов (§5) и файл пользователя `keymap.json` в каталоге состояния (§8). Файл сильнее вкладов; без файла действуют одни вклады.

## Файл пользователя

```json
[
  { "key": "Ctrl+Alt+N", "mac": "Cmd+Alt+N", "command": "claude.newSession" },
  { "key": "Ctrl+Shift+M", "mac": "Cmd+Shift+N", "command": "claude.newSession", "args": { "category": "work" } },
  { "key": "J", "command": "sessions.next", "when": "sessions.list" },
  { "mac": "Cmd+W", "command": null }
]
```

- Массив записей `{key?, mac?, command, args?, when?}`, хотя бы одна из `key` и `mac` (`mac: null` без `key` — проблема записи: связывать нечего). `command` — id команды из вкладов, `args` уходит в команду как есть.
- `mac` заменяет `key` на macOS. Запись только с `mac` на Linux не действует; запись только с `key` действует на обеих платформах; `key` вместе с `"mac": null` действует только на Linux, на macOS записи нет (как `command: null` значит «команды нет», так `mac: null` значит «клавиши на macOS нет»). Остальной `mac`, не строка и не `null`, — проблема записи. Каталог конфига бывает общим для мака и Linux, поэтому одна запись описывает обе.
- `when` — тип панели, у которой фокус (`sessions.list`, `claude.transcript`). Без `when` клавиша действует в любой панели. Так буквы работают в списке, а `Ctrl+\` — отовсюду, как в прежнем TUI. `Ctrl+\` («фокус в список») — вклад `shell.focusList` встроенного плагина `shell` (см. «Команды окна»), его пользователь переопределяет или снимает в `keymap.json`.
- `command: null` снимает клавишу с тем же `when`: и у вкладов, и у записей файла выше неё. Записи с другим `when` она не трогает: чтобы снять клавишу вклада в панели, `when` пишется тот же, что у вклада.
- Файл правит пользователь руками; по запросу окна его пишет и `roostd` (см. «Запись из окна»). Id плагина `keymap` зарезервирован: иначе файл состояния плагина `<id>.json` (§8) совпал бы с файлом хоткеев.

## Разрешение

Таблица ключуется парой (клавиша, `when`). Внутри пары действует одна запись:

1. Нижняя запись файла, как в `keybindings.json` VS Code (https://code.visualstudio.com/docs/configure/keybindings).
2. Иначе — вклад первого по порядку загрузки плагина (§5). Проигравший вклад — проблема. Вклад, перекрытый файлом, проблемой не считается, палитра показывает его как переопределённый.

На нажатие сначала ищется пара с `when` панели в фокусе, затем пара без `when`. Поэтому запись пользователя без `when` не перекрывает вклад с `when` в его панели: для этого пишется запись с тем же `when`. Реестр вкладов (`PluginRegistry::Keys_`, `src/roostd/manifest.{hpp,cpp}`) ключуется этой парой: разобранная клавиша и `when`. Два вклада `J` в разных панелях не конфликтуют; одна пара у двух плагинов — конфликт, проигравший получает проблему. `KeyOwner(key, when)` ищет владельца пары; без `when` — пару без `when`.

## Клавиша

- Запись — модификаторы через `+`, затем одна клавиша: `Cmd+Shift+N`, `Ctrl+\`, `Alt+Left`, `F5`, `J`. Модификаторы: `Ctrl`, `Alt` (Option на macOS), `Shift`, `Cmd` (только macOS). Регистр и порядок модификаторов не важны. `+` как клавиша пишется в конце: `Ctrl++`. Имена клавиш: одна буква или другой одиночный символ, `Left`, `Right`, `Up`, `Down`, `Home`, `End`, `PageUp`, `PageDown`, `Insert`, `Delete`, `Backspace`, `Enter` (`Return`), `Tab`, `Space`, `Escape` (`Esc`), `F1`–`F24`; другое имя — ошибка. Буква в записи латинская, с диакритикой можно (`É`); буква другого письма — ошибка, пишется клавиша US (`Ctrl+;`, а не `Ctrl+ж`).
- Нормальный вид (`WriteKeyChord`, `src/core/key_chord.cpp`): модификаторы в порядке `Cmd`, `Ctrl`, `Alt`, `Shift`, затем клавиша; одна буква заглавная, имя в каноническом написании. `Shift+Ctrl+k` пишется `Ctrl+Shift+K`; разбор нормального вида даёт ту же клавишу.
- Разбор — `ParseKeyChord(text, platform)` в `src/core/key_chord.{hpp,cpp}`, без Qt кроме `QString`. Платформа — аргумент (`EPlatform`), а не `#ifdef`: тест одного бинарника проверяет обе. Платформа сборки — `HostPlatform()`. `ChooseKeyChord(key, mac, platform)` берёт клавишу записи: `mac` на macOS, иначе `key`; `key` проверяется как клавиша Linux, `Cmd` в ней — ошибка, а оба поля проверяются на любой платформе, чтобы общий файл читался одинаково.
- `Cmd` в клавише, которая действует на Linux, — проблема записи. Super на Linux занят рабочим столом, и приложение нажатие часто не получает; поэтому `Cmd` пишется в `mac`.
- Имя модификатора значит физическую клавишу. `QKeySequence` для разбора не подходит: в Qt `Key_Control` на macOS — это ⌘, а `Key_Meta` — Control (https://doc.qt.io/qt-6/qt.html#Key-enum), и `Ctrl+N` из конфига сработал бы на ⌘N. Тот же сдвиг уже учитывает `IsCopyShortcut` (`src/terminal/qt_key_mapping.hpp:79-86`).
- Клавиши сравниваются в разобранном виде: набор модификаторов и код клавиши. Поэтому `Shift+Ctrl+N` и `Ctrl+Shift+N` — одна клавиша.
- Буква сопоставляется по символу текущей раскладки, если раскладка латинская, иначе по физическому положению на раскладке US. `Cmd+Z` на Dvorak остаётся на клавише с буквой Z, а `J` срабатывает и на русской раскладке, как в прежнем TUI. Физическая клавиша берётся из `nativeVirtualKey` на macOS (`kVK_ANSI_*`) и из `nativeScanCode` на Linux (код xkb = evdev + 8). Раскладка — свойство раскладки, а не нажатой клавиши: Qt не отдаёт текущую раскладку одинаково на macOS и Linux (`QInputMethod::locale()` на Linux с xcb и Wayland даёт локаль системы, а не раскладку), поэтому её судят по буквенным клавишам. Нажатие клавиши US A–Z, которая печатает букву нелатинского письма, делает раскладку нелатинской; нажатие, печатающее латинскую букву, — латинской, но латинская буква с Ctrl, Alt или Meta не считается, потому что с ними часть платформ отдаёт латинский символ другой группы раскладки. Символ, цифра и особая клавиша ничего не говорят: Dvorak печатает символ на месте буквы и остаётся латинской. Решение держится, пока не придёт следующая буква (`ObserveLayout`, `NonLatinLayout`, `src/terminal/physical_keys.hpp`); до первой буквы раскладка латинская, а после смены раскладки символьная клавиша ещё судится по прежней: после русского текста на латинской раскладке не US (QWERTZ, AZERTY) символьная клавиша сопоставляется по клавише US до следующей буквы, и `-` QWERTZ на клавише US `/` запускает `Ctrl+/`, а не `Ctrl+-`; раскладку у ОС спросит #206. На нелатинской раскладке буква и символьная клавиша сопоставляются по клавише US на этом месте, а Shift выбирает символ с Shift: `Ctrl+/` срабатывает на клавише US `/`, которая на русской раскладке печатает `.`, а Shift+4 (`;` на русской) — это `Ctrl+Shift+4`, не `Ctrl+;`. На латинской раскладке символьная клавиша сопоставляется по своему символу. Решение принимает `BindingKey`; оба фильтра событий (`KeyMatcher`, `RoostSingleton`) передают в `ObserveLayout` каждое нажатие.
- Shift и символьная клавиша. `Ctrl++` и `Ctrl+Shift+=` — одна физическая клавиша на раскладке US, а событие приходит с `+` и Shift, или с `=` и Shift, смотря на раскладку. Правило: Shift с цифрой или символьной клавишей раскладки US входит в символ, а не остаётся модификатором. `Ctrl+Shift+=` значит то же, что `Ctrl++`; `Cmd+Shift+4` — то же, что `Cmd+$`. С буквой, именем клавиши (`Tab`, `Left`) и клавишей F1–F24 Shift остаётся модификатором: `Ctrl+Shift+N`, `Shift+Tab`. Правило применяется к обеим сторонам, к записи таблицы и к событию (`MatchForm`, `src/api/keymap_service.cpp`), поэтому любое из двух написаний срабатывает на нажатие Shift+`=` с Ctrl, а `Ctrl+=` — только на `=` без Shift. Две записи таблицы, ставшие одной парой (`Ctrl++` и `Ctrl+Shift+=`), оставляют первую.
- Последовательностей вида `Cmd+K Cmd+S` в v1 нет: в прежнем TUI их нет, а ожидание второго нажатия задерживает первое.

## Ввод текста

- Когда фокус в терминале или в поле ввода, нажатие сначала ищется в таблице, и только непойманное уходит в PTY или в поле. Пойманная клавиша у программы и у поля отбирается.
- Поэтому клавиша без `Cmd`, `Ctrl` и `Alt`, кроме F1–F24, в терминале и в поле ввода не срабатывает ни с каким `when`. Без `when` она — проблема записи: действовать ей негде, кроме панелей без ввода, а там её место — `when` этой панели. Запись `command: null` под это не подпадает: она ничего не привязывает, а только снимает.
- `Ctrl` с буквой в терминале — управляющий символ для программы, `Alt` с буквой на macOS набирает символ. Такие клавиши срабатывают, но палитра помечает их как «перехватывает ввод».
- Пока метод ввода (IME) собирает символ, таблица не просматривается: нажатие принадлежит IME.
- Что считается вводом текста: терминал (`TerminalItem`) и элемент с флагом `ItemAcceptsInputMethod` (`TextInput`, `TextEdit`). IME считается собирающим, пока последнее событие метода ввода несёт непустой preedit.

## Вклады плагинов

- Вклад — та же запись без `args`, с обязательной `command`: `{ "command": "claude.newSession", "key": "Ctrl+Alt+N", "mac": "Cmd+Alt+N" }`. Ключ `mac` взят у `contributes.keybindings` VS Code (https://code.visualstudio.com/api/references/contribution-points).
- Неразборная клавиша во вкладе — проблема: вклад не действует, остальной манифест грузится. Текст проблемы: `keybinding <номер с 0 в массиве вкладов> of plugin <id> is ignored: "key": <сообщение разбора>` (или `"mac"`). Клавиши разбирает реестр при `Add`; `ParseKeybindings` отвергает манифест только за структуру: нет id команды, ни `key`, ни `mac`, не строка в `key`, `mac` или `when`, команда другого плагина. Вклад только с `mac` на Linux не действует и проблемой не считается.
- Вклад без `Cmd`, `Ctrl` и `Alt` (кроме F1–F24) и без `when` — проблема, он не действует, как и такая запись файла (см. «Ввод текста»). Текст: `keybinding <номер> of plugin <id> is ignored: <клавиша> has no Cmd, Ctrl or Alt: without "when" it would take the text typed into any panel`. Такая клавиша с `when` панели допустима.

## Команды окна

Команды без бэкенда исполняет само окно; клавиши, `null` и конфликты для них решает `roostd` вместе со всеми остальными: так нет второго места, где решается, чья клавиша.

- Объявляет их встроенный плагин `shell` (`plugins/shell/plugin.json`): только `contributes.commands` и `contributes.keybindings`, без QML и бэкенда. Цена: плагин без панелей виден в `plugins.list`. Альтернатива «клавиши окна зашиты в окне и подмешиваются под таблицу `roostd`» отвергнута: `null` пользователя и конфликты для них решались бы в двух местах; «`roostd` возвращает `commands.run` окну событием» — лишний круг на каждое нажатие и новое событие.
- Обработчик — в реестре `CommandService` окна (`src/api/command_service.{hpp,cpp}`, `Register`, образец — `Dispatcher::Register`). `Run` смотрит в реестр до `roostd`: команда с обработчиком исполняется в окне, и запрос `commands.run` не уходит; любой другой id идёт в `roostd`, как раньше. У команды может быть несколько обработчиков (по одному от каждой панели, например двух терминалов): `Run` идёт по записям от последней к первой и берёт первую, у которой нет проверки фокуса или панель-владелец сейчас в фокусе (`activeFocus` корня панели; панель запись получает от загрузчика плагинов, `bindCallOwnerPanel`); если в фокусе ни одной, берётся панель, у которой фокус был последним (`CommandService::NoteFocus`, его зовёт `CommandsAdapter` по `activeFocusChanged` панели; ссылка слабая), а если и такой нет, последняя из зарегистрированных живых. Конец владельца снимает только его записи, так что панель, пересозданная до уничтожения старой, и вторая из двух панелей команду не теряют. Так `terminal.copy` при двух терминалах копирует выделение того, что в фокусе, а когда фокус ушёл из обоих (диалог, список, неактивное окно, `commands.run` снаружи), — того, где человек работал последним. Обработчик из QML оболочки панели не имеет и выбирается только по порядку регистрации. Из QML — `Roost.commands.registerCommand(id, handler)` (§5): обработчик живёт, пока жива панель, которая его поставила (владелец вызовов, §5), а из QML оболочки — пока живо окно.

- `sessions.newSession` (вклад плагина `sessions`) объявлен в его манифесте, а обработчик ставит окно рядом с `layout.*`: список, в котором открыть форму, зависит от связей панели с клавиатурой (как у `shell.focusList`), а обработчик панели `sessions` получил бы команду только от списка в фокусе или бывшего в фокусе последним, не от связанного с терминалом. `Cmd+N` нигде больше не занят; на Linux `Ctrl+N` остаётся программе в терминале, поэтому там `Ctrl+Shift+N`, и палитра помечает её «перехватывает ввод». Пользователь переносит или снимает клавишу в `keymap.json`.
- Клавиши размера шрифта (вклад плагина `terminal`, обработчик в окне, как у `sessions.newSession`): размер один на все окна и панели, команды пишут документ `settings` (05-plugins.md, «Roost.theme»), поэтому обработчик в `Main.qml`, а не в `TerminalPanel.qml`: панелей терминала может быть ноль или две, а полоса проблем, где команда на пределе объясняет отказ, принадлежит окну. На Linux клавиши с `Shift`, потому что `Ctrl+=`, `Ctrl+-` и `Ctrl+0` нужны программе в терминале; по правилу «Shift и символьная клавиша» выше Shift входит в символ, так что `Ctrl+Shift+=` значит ту же клавишу, что `Ctrl++` (приходит как `Key_Plus` с Shift, а `Ctrl+Shift+-` — как `Key_Underscore`). `Ctrl+Shift+-` на Linux — это `Ctrl+_`, отмена в readline и emacs: окно забирает её у программы в терминале; перенести или снять клавишу можно записью в `keymap.json`.
- `Ctrl+Shift+P` (на macOS `Cmd+Shift+P`) — клавиша палитры: среди вкладов встроенных плагинов она свободна. На Linux это `Ctrl` с буквой, поэтому палитра помечает её «перехватывает ввод»: программа в терминале, которой нужна эта клавиша, её не получит; пользователь переносит палитру записью в `keymap.json`. Палитра открывается ещё кнопкой панели инструментов (Linux) и пунктом меню View (macOS). `Shortcut` без таблицы у палитры нет: без `roostd` команд нет, и показывать нечего.
- `Cmd+Shift+B` на Linux не занят: `Ctrl+Shift+B` принадлежит программе в терминале. Окно отчёта открывается ещё кнопкой панели инструментов (Linux) и пунктом меню Help (macOS). Окно настроек — кнопкой «Settings…» панели инструментов (Linux) и пунктом «Settings…» меню (macOS); клавиши на Linux у `shell.settings` нет.
- Это записи таблицы, а не `Shortcut` окна: Qt проверяет `Shortcut` раньше, чем нажатие доходит до фильтра `KeyMatcher` (`QShortcutMap` отрабатывает на `ShortcutOverride`, до `KeyPress`), так что клавиша, занятая включённым `Shortcut`, в таблице не находилась бы и `keymap.json` её не переопределял. Исключение — два `Shortcut` в `Main.qml` (`Ctrl+\` и `Cmd+Shift+B` на macOS), включённые только пока в окне нет таблицы (`Roost.keymapLoaded` ложно: до первого ответа `keymap.get`, при упавшем или недоступном `roostd`, без манифеста `shell`): отчёт об ошибке должен открываться именно тогда, когда `roostd` сломан. Как только таблица загружена, они выключены и клавишу получает только `KeyMatcher`, двойного срабатывания нет. Другой `Shortcut` добавлять нельзя по той же причине.
- Запись плагина `shell` без обработчика в окне клавишу не забирает: `KeyMatcher` пропускает нажатие дальше, а не шлёт команду в `roostd` за -32003 (у `terminal.copy` это путь `IsCopyShortcut`). Признак — источник записи `shell`; запись пользователя с командой `shell` под этот признак не подпадает.
- Копирование: `IsCopyShortcut` (`src/terminal/qt_key_mapping.hpp`) остаётся запасным путём в `TerminalItem` на тех же клавишах всякий раз, когда запись таблицы нажатие не забрала: таблицы нет (демон не отвечает), обработчика `terminal.copy` в окне нет или клавишу занял пользователь (`null` для `terminal.copy` её не снимает).
- Клавиши таблицы не срабатывают, пока фокус в `Popup` или `Dialog` (клавиши принадлежат диалогу) и пока идёт сборка IME; кодом это не меняется.
- Вставки в таблице пока нет: у терминала нет клавиши вставки, команда `terminal.paste` появится с ней.
- Команды `layout.*` действуют на панель в фокусе, иначе на последнюю бывшую в фокусе, то же делает контекстное меню панели (`06-panels.md`, «Правка раскладки»); клавиш по умолчанию нет, их задаёт `keymap.json`.

## Палитра

Палитра (`src/roost/CommandPalette.qml`, строки — `PaletteModel`, `src/roost/palette_model.{hpp,cpp}`) — оверлей окна над общим списком команд: по строке на каждую команду из `contributes.commands` манифестов в `plugins.list`, включая команды окна плагина `shell`, в порядке загрузки плагинов, затем в порядке манифеста. Команда без объявления в манифесте в палитре не появляется (§5, `registerCommand`). Строки берутся из кеша `plugins.list` и из окнной копии таблицы клавиш и пересобираются по `Changed` обоих: правка `keymap.json` видна в открытой палитре.

- Открытие: команда `shell.palette`. Фильтр по буквам: буквы строки по порядку, между ними что угодно, регистр не важен, ищется по названию и по id команды. Строки не ранжируются: остаются в базовом порядке, поэтому результат устойчив. Стрелки двигают выбор, Enter запускает выбранную команду через `Roost.commands.run` (путь §5: обработчик окна, иначе `roostd`) после закрытия палитры, Escape закрывает без запуска. Закрытая палитра возвращает фокус элементу, у которого он был. Ошибка команды попадает в лог предупреждением, как у `run` без колбэка.
- Вид: окно по центру окна приложения, карточка стиля (18-style.md): `surface`, радиус `radiusCard`, линия `line` 1 px и мягкая тень из нескольких полупрозрачных скруглённых прямоугольников. Ширина 304, не больше окна за вычетом `windowMargin` с каждой стороны; высота по содержимому (заголовок, поле поиска, строки, подвал), но не больше потолка: половины высоты окна, и не меньше подвала с шапкой и одной строки, и не больше окна за вычетом тех же полей, берётся меньшее; потолок и высота в целых пикселях, никогда не отрицательные; верх карточки стоит там, где он был бы у карточки высотой с потолок по центру окна, поэтому при наборе карточка растёт и сжимается только вниз, а заголовок и поле не прыгают; у списка минимум одна строка (47); не поместившиеся строки прокручиваются, заголовок, поле и подвал остаются, выбранная строка остаётся на виду, в том числе при уменьшении окна. Без строк карточка высотой с заголовок, поле, строку «No commands.» (или «No command matches.») и подвал. Сверху заголовок «Commands» (`titleFont`) и строка `metaFont` DemiBold цветом `focus` с точкой 8 px: «Input in commands · Esc to close». Поле поиска высотой 40, радиус `radiusControl`, рамка `focus` толщиной `cursorRingWidth` (в палитре фокус у поля всегда), значок `⌕` и заглушка «Action or session» цветом `textMuted`. Строки высотой 47 (выше, если есть конфликт), радиус `radiusControl`, отступ 12 по бокам: в первой строке название — `rowFont` DemiBold, справа клавиша `smallFont` цветом `textSecondary` не шире 45% строки, длинная обрезается многоточием справа; во второй строке `плагин · id команды` (обрезается справа) и пометки «keymap.json» и «captures input» (не обрезаются); выбранная строка — `selectedBackground`, строка под мышью — `hoverBackground`. Групп нет: модель плоская, заголовков групп палитра не рисует. Внизу линия `line` и подсказка `metaFont` цветом `textSecondary`: «↑↓ select · Enter run» и «Esc back». Команды, фильтр, клавиши, выбор и возврат фокуса от вида не зависят.
- Клавиша: все клавиши таблицы, которые запускают команду, через запятую; у клавиши с `when` он стоит после неё в скобках: `Ctrl+Alt+L (sessions.list), Ctrl+Alt+L`. Выбор строки переживает пересборку: после правки `keymap.json` или смены `plugins.list` выбрана та же команда, а если её больше нет, первая строка.
- Конфликт: клавиша вклада, которую заняла запись другого плагина (проигравший вклад, §«Разрешение»). Окно находит его само: клавишу вклада из манифеста (`ChooseKeyChord` для платформы окна) сопоставляет с парой таблицы; если её держит другой плагин, строка победившей и строки проигравших называют всех: `<клавиша> is bound by <победитель> and <проигравший>: <победитель> keeps it, <проигравший> is ignored`. Проигравших у одной клавиши несколько — одна фраза на клавишу, каждый назван один раз: `<клавиша> is bound by <победитель>, <проигравший 1> and <проигравший 2>: <победитель> keeps it, <проигравший 1> and <проигравший 2> are ignored`. Текстов проблем `keymap.get` окно для этого не разбирает.
- Переопределено пользователем: у команды есть клавиша таблицы с источником `user`, либо клавишу её вклада заняла запись файла (строка проигравшей команды помечена, клавиши у неё нет). Снятая `command: null` клавиша не помечается: в таблице от неё не остаётся следа, а отличить её от клавиши, отброшенной проблемой, по таблице нельзя.
- Перехватывает ввод: клавиша команды — `Ctrl` с буквой или, на macOS, `Alt` с буквой (см. «Ввод текста»), действующая в терминале: без `when` или с `when` `terminal.view`. `Ctrl+\` не помечается: это не буква.

## Запись из окна

Окно файл не пишет: каталог состояния принадлежит демону (ADR 014). Окно просит `roostd` двумя методами (§4), каждый правит записи одной команды, остальной файл не трогает:

- `keymap.setCommand {command, args?, when?, entries}` задаёт весь набор клавиш команды одним вызовом: одна запись файла, одно изменение таблицы. `entries` — массив `{key?, mac?}`, как в файле, и только эти два поля: `command`, `args` и `when` берутся из запроса. Это все клавиши, которые должны быть у команды (с этими `args` и `when`) после вызова, на каждой платформе; клавиша вклада, которую команда сохраняет, тоже перечисляется. Добавить клавишу — отправить текущие клавиши и новую; `[]` снимает все. Демон считает остальное сам:
  - записи файла с той же `command`, теми же `args` (нет и `null` — одно и то же) и тем же `when` (нет — пустой) заменяются записями `entries`; новые ставятся в конец массива (нижняя запись сильнее, «Разрешение»);
  - клавиша, которую вклады дают команде для этого `when` (вклады не дают `args`) и которой нет в `entries`, снимается записью `command: null` с тем же `when`. Такие записи ставятся в начало файла: они снимают клавишу вкладов, но не записи файла, которые связывают ту же клавишу ниже (в том числе чужую запись, занявшую клавишу команды: когда она уйдёт, клавиша не вернётся команде);
  - клавиша вклада, которая есть в `entries`, своей записи не получает (не дублируется); исключение — клавиша, которую занимает другая запись файла: тогда пишется и она, и как последняя выигрывает;
  - записи `command: null`, которые прошлый вызов поставил для этой команды, убираются и составляются заново. «Поставил для этой команды» значит: запись, которая на каждой платформе, где действует, снимает только клавиши этой команды (с этими `args` и `when`) и хотя бы на одной платформе снимает одну. Вручную написанная запись, снимающая клавишу другой команды или никакую, остаётся.
- Запись `command: null`, снимающая клавиши вкладов, составляется так, чтобы на каждой платформе снимать только клавиши этой команды. Запись с `key` действует на Linux и, без `mac`, на macOS; `mac` задаёт клавишу macOS; `mac: null` оставляет macOS без записи. Поэтому клавиши macOS и Linux, которые команда имеет от вкладов, идут парами `{key, mac}` по порядку таблицы (число клавиш на платформах бывает разным: клавиша проигрывает конфликт другому плагину на одной платформе). Лишняя клавиша macOS получает запись с одним `mac`, лишняя клавиша Linux — запись `{key, "mac": null}`: клавиша другой команды на macOS остаётся. `resetCommand` узнаёт такие записи по действию: запись `command: null` его, если она снимает только клавиши вкладов этой команды и не трогает клавишу записи файла выше неё; другая запись, держащая ту же клавишу, на это не влияет. Повтор `setCommand` с тем же набором файл не пишет.
- `keymap.resetCommand {command, args?, when?}` возвращает команду к вкладам: убирает то, что записывает `setCommand` для этих `args` и `when`: записи команды и записи `command: null`, снимавшие только её клавиши (правило выше). Клавиши с другим `when` не трогаются. Записи `command: null`, которые снимают клавишу другой команды (написанные вручную), остаются. Команды, которой нет ни у одного плагина, это не ошибка: её записи уходят всё равно.

Что проверяется и чем отказ:

- `InvalidParams`, файл не тронут: `command` не id команды плагина (для `setCommand`), `entries` не массив (`null` тоже отвергается), запись не объект, клавиша не разбирается тем же `ChooseKeyChord`, что и в файле, ни `key`, ни `mac`, поле записи кроме `key` и `mac`, клавиша без `Cmd`, `Ctrl`, `Alt` и без `when` (запись файла с ней была бы проблемой). Одна запись, которую отвергают, отвергает весь вызов: файл не тронут. Клавиша проверяется как для macOS, так и для Linux: файл общий.
- `StoreFailed` (-32004), файл не тронут: файл не JSON, не массив, больше 1 МиБ (и после правки тоже), не читается или не пишется. Файл читается заново при каждом вызове, а не берётся из того, что демон помнит: правка руками между вызовами не затирается. Неразборный файл не переписывается: руками набранный текст другой копии не имеет, пользователь чинит его сам.
- Вызов, который ничего не меняет (`resetCommand` команды без записей, повтор того же `setCommand`), файл не пишет и не создаёт.

Запись атомарная (`QSaveFile`): временный файл рядом, `rename`. Нет файла или каталога — создаются так же, как документы хранилища (§8): созданный каталог 0700, файл 0600. Обработчик выполняется в цикле событий до конца, поэтому вызовы двух окон не перемежаются: второй читает файл, который записал первый. Что теряется: файл пишется заново как JSON с отступами, поэтому пробелы и форматирование не сохраняются; комментариев в файле нет (ADR 014), с другими способами разметки он не читается. Порядок и содержимое записей других команд сохраняются. Событие `keymap.changed` приходит так же, как при правке руками: его публикует слежение за файлом, второго пути объявления нет, ответ метода таблицу не несёт.

## Окно настроек как автор

Раздел «Keys» окна настроек (`src/roost/SettingsWindow.qml`, диалог `src/roost/KeyCaptureDialog.qml`, помощник `KeyChords`, `src/roost/key_chords.{hpp,cpp}`) правит клавиши через `keymap.setCommand` и `keymap.resetCommand` (`Roost.call`), файл не пишет. Окно вправе менять любую команду; плагин через `Roost.call` — только те, что он объявил в своих `contributes.commands` (§5, «Вызовы из QML»).

- Строки: по одной на команду из `contributes.commands` и на каждую пару (`args`, `when`), для которой у неё есть клавиши в таблице или от вкладов; команда без клавиш — одна строка с пустым `when`, чтобы дать ей клавишу. Клавиша `user` помечена. У строки «Add key», у каждой клавиши «×» и «Reset».
- «Reset» (`keymap.resetCommand`) — по строке, а не по команде: он снимает то, что записано для этих `args` и `when`, как `setCommand`, чей ключ тот же; строки одной команды с другими `args` или `when` он не трогает. Показан у строки, которую пользователь менял, то есть когда сброс что-то уберёт из файла: в таблице у строки есть клавиша `source: "user"`, или клавиши, которую даёт её вклад (для платформы окна и этого `when`), в таблице нет и никто её не держит (пользователь её снял: запись `command: null`). Клавиша вклада, которую держит другая команда (запись файла другой команды, или вклад другого плагина), не повод для «Reset»: сброс этой строки чужой записи не касается и ничего бы не изменил. Вместо него строка пишет приглушённым текстом `<клавиша> is held by <команда>`; «Reset» появится у строки, у которой есть собственная запись.
- Захват: «Add key» открывает модальный диалог, в нём нажатие — ответ пользователя. Диалог, а не режим строки, потому что `KeyMatcher` уступает нажатие тому, у кого фокус в `Popup` или `Dialog` («Кто читает и кто исполняет»): в строке нажатая клавиша запустила бы команду, которой она назначена. Клавиша записывается так, как `KeyMatcher::ChordOf` называет нажатие (раскладка, физические модификаторы, `Cmd` только на macOS), текстом, который разбирает `ChooseKeyChord`. `Escape` и «Cancel» закрывают диалог, ничего не записав. Клавиша, у которой нет имени в таблице (один модификатор), игнорируется. Отказ `roostd` (клавиша без `Cmd`, `Ctrl` и `Alt` при пустом `when`, буква другого письма) показан в диалоге его причиной, диалог остаётся открытым для другой клавиши, файл не тронут. Клавиша, которая у команды уже есть, записи не вызывает: диалог так и говорит.
- Набор клавиш. Один вызов `keymap.setCommand` несёт все клавиши команды (с этими `args` и `when`) на обеих платформах, потому что `roostd` снимает записью `command: null` клавишу вклада, которой в `entries` нет, на каждой платформе. Окно держит таблицу своей платформы; другую читает `keymap.get {platform}` перед каждой записью и отправляет как есть. Запись для набора: клавиша, одинаковая на обеих платформах, — `{key}`; клавиша только этой платформы — `{mac}` на macOS и `{key, "mac": null}` на Linux (действует только здесь, чужая платформа не получает клавишу и не теряет прежнюю); клавиша только другой платформы — так же, наоборот. Поэтому клавиша, которую снимают на macOS, остаётся на Linux записью `{key, "mac": null}`, если запись файла была общей: окно не решает за платформу, которой не видит. Клавиш только для Linux окно с macOS не создаёт, но, отправляя набор, сохраняет.
- Конфликт проверяется до записи. Если захваченная клавиша (пара «клавиша, `when` строки», платформа окна, окно ищет её в своей таблице тем же `Find`, что и нажатие) занята другой командой (или той же с другими `args`), диалог пишет: `<клавиша> is bound to <название команды>; it will lose this key`, и две кнопки, «Confirm» и «Cancel». «Cancel» и `Escape` ничего не пишут. Предупреждение объявлено вспомогательным технологиям (`Accessible.role: AlertMessage`, `Accessible.announce`, когда появляется), клавиатура в нём на «Cancel». «Confirm» пишет два вызова и держит диалог открытым до конца обоих: сначала `setCommand` для команды окна с новой клавишей (запись встаёт в конец файла и по «Разрешению» побеждает: с этого момента таблица держит клавишу за ней, и она нигде не оказывается на двух командах), затем, когда таблица с первым вызовом пришла в окно, `setCommand` для прежнего держателя с его набором без этой клавиши (его запись файла уходит, клавишу вклада снимает запись `command: null`). Для таблицы хватило бы первого вызова, для файла нет: запись или вклад прежнего держателя остались бы под побеждающей записью, и когда получателя сбросят или у него снимут клавишу, она вернулась бы прежнему держателю, которому окно сказало, что он её теряет. Наборы второго вызова и первого составляются из таблицы в момент вызова, а не из той, что была при открытии диалога: клавиша, которую команда получила за это время (другое окно, правка файла), не теряется. Если к «Confirm» держатель сменился, окно предупреждает о новом и ничего не пишет; если клавиша стала клавишей самой команды, говорит об этом и ничего не пишет. Порядок «сначала получатель»: ошибка первого вызова ничего не меняет и показана в диалоге, ошибка второго оставляет верную таблицу (клавиша у получателя) и показана в диалоге словами «`<команда> has <клавиша> now, but <держатель> could not give it up: <причина>`»; диалог остаётся для другой клавиши, а тот же текст остаётся под заголовком «Keys» (`keysError`) после его закрытия. Двух вызовов атомарность не охватывает; промежуточная таблица между ними тоже верна: клавиша уже у получателя.
- Запись ждёт таблицу. После вызова окно не принимает следующего действия над клавишами (захват клавиши в диалоге, «×», «Add key», «Reset» и «Confirm» отключены, под заголовком «Keys» стоит «Saving the keys…», диалог говорит «Saving the key…»), пока в окно не пришла таблица, которая следует за записью, потому что `roostd` публикует её через 100 мс после записи (§16 ниже), а набор клавиш следующего действия составляется из таблицы окна: из таблицы без первой записи вторая стёрла бы первую. Таблицей, которая следует, считается первый `keymap.changed` (или ответ `keymap.get` после переподключения) после ответа на вызов. Окно не зависает, если её нет: вызов кончился ошибкой — запись кончена с ней; ответ без ошибки, а таблицы нет (вызов, который ничего не меняет, файл не пишет и события не даёт; потерянное событие) — запись кончается по `keysWriteTimeout` (3 с с вызова и ещё столько же после ответа), без ошибки; ответ, который пришёл после этого, окно принимает как правду: запись, на которую он ответил (последняя), могла дойти, а «roostd did not answer…» нет. Успех стирает этот текст (под заголовком «Keys» и в диалоге), ошибка заменяет его причиной; таблица, которая за ответом следует, принимается как любая другая (окно берёт каждую), а действия над клавишами этот ответ не повторяет: набор следующего из них составился бы из таблицы, где его записи ещё нет. Следующий вызов, пришедший во время записи не из кнопок (код, не смотрящий на них), отказан с «The previous change of the keys is still being saved»: очереди нет. Образец состояния — `promptStarting` панели сессий (§6).
- Вызов хелперов окна кодом плагина отказан (§5, «Вызовы из QML»): ключи плагина правит `Roost.call`, а не `Window.window.setKeys`.
- Доступность и клавиатура. В диалоге `Tab` и `Shift+Tab` без других модификаторов идут дальше по кнопкам, а не захватываются, и назначить их из окна нельзя даже строке с `when`, где `roostd` их принял бы (без `when` он отверг бы их и так); файл их привязать может. `Ctrl+Tab` и подобные захватываются. Клавиатура после записи остаётся там, где пользователь был: таблица пересобирает строки, а кнопка, у которой она стояла, отключена на время записи; поэтому окно запоминает действие и по его концу ставит фокус сам: после «Add key» (диалог закрылся) на «Add key» той же строки, после «×» на «×» следующей клавиши строки, а если её нет, на «Add key», после «Reset» на «Add key» той же строки. Если строка исчезла (у неё снята последняя клавиша и у команды есть другие строки), фокус идёт на первую строку команды. Если пользователь за это время ушёл на другой элемент окна, фокус у него не отбирается. `Super` (Meta в Qt, клавиша Windows) на Linux игнорируется: нажатие с ним не даёт клавиши ни в диалоге, ни у `KeyMatcher` (`ChordOf`), и в таблицу Linux клавиша с `Super` не попадает; `Cmd` есть только на macOS.
- Чего нет: клавиш с `when`, отличным от того, что у строки (диалог пишет в строку, у которой открыт), клавиш для другой платформы, проверки конфликта на другой платформе (новая клавиша действует только на платформе окна, набор выше, поэтому чужого конфликта она не создаёт), последовательностей. Список команд — из `plugins.list`; таблицы без команды плагина (стоящие в файле записи неизвестных команд) в разделе не видны.

## Кто читает и кто исполняет

- Файл читает `roostd` и по запросу окна пишет (`KeymapService`, `src/roostd/keymap_service.{hpp,cpp}`): у него уже есть реестр вкладов с конфликтами (`src/roostd/manifest.cpp`) и каталог состояния (§8). Вклады для платформы запроса реестр выбирает тем же `ChooseKeyChord`, а демон на другой платформе строит для неё свой реестр из тех же манифестов. Окно держит копию таблицы своей платформы (`KeymapService`, `src/api/keymap_service.{hpp,cpp}`): `keymap.get` после соединения, замена по каждому `keymap.changed` своей платформы, сброс при разрыве и новый запрос после возвращения демона, как у `StoreService`. Окно запрашивает таблицу методом `keymap.get {platform}`, а после правки файла получает событие `keymap.changed` (§4). Платформу называет окно: демон может работать на другой машине (§14).
- Запись итоговой таблицы — `{key, command, args?, when?, source}`, где `key` уже приведён к платформе окна, а `source` — `user` или id плагина. Окно сопоставляет нажатие с таблицей в GUI-потоке поиском по хешу и файлов не читает. Порядок записей: вклады в порядке загрузки плагинов, затем клавиши файла, которых вклады не занимали; перекрытая клавиша остаётся на месте вклада. Таблица, которая не помещается в кадр, — `InternalError` у `keymap.get`, как у `sessions.list`; событие `keymap.changed` для такой таблицы не публикуется, демон пишет `qWarning`.
- Нажатие сопоставляет `KeyMatcher` (`src/roost/key_matcher.{hpp,cpp}`), фильтр событий приложения: только `KeyPress` окна, не при сборке IME и не пока таблица не загружена. Тип панели в фокусе — свойство `panelType` ближайшего предка активного элемента с `objectName` «panelSlot» (так панели находит и `Shell`); вне панели `when` не ищется. Пока активный элемент лежит под `QQuickOverlay` окна (в `Popup` или `Dialog`, например в окне отчёта об ошибке), таблица не смотрится и клавиши достаются диалогу. Отпускание клавиши глотается, только если её нажатие поймано в том же окне с фокусом: смена окна в фокусе забывает пойманные нажатия. Смена объекта в фокусе сбрасывает флаг сборки IME. Поиск: пара (клавиша, тип панели), затем (клавиша, без `when`). Найденная клавиша запускает `CommandService::Run(command, args)` и не доходит до элемента; её автоповтор не запускает команду повторно, а отпускание не доходит до элемента. Ошибка команды пишется `qWarning`.
- Нажатие обрабатывает окно, у которого фокус; `keymap.changed` приходит всем окнам. Команду окно запускает так же, как палитра. Команда, у которой в окне есть обработчик, исполняется в окне, не доходя до `roostd` (см. «Команды окна»).
- Изменения отслеживает `QFileSystemWatcher` на файле и на каталоге. После `rename` Qt перестаёт следить за файлом (https://doc.qt.io/qt-6/qfilesystemwatcher.html), а редактор, который сохраняет через временный файл, делает именно `rename`; событие каталога возвращает файл под слежение. Файл перечитывается через 100 мс после последнего события, чтобы не разбирать его посреди записи. Событие, которое не меняет файл (чтение меняет время доступа, запись соседнего документа каталога меняет каталог), не считается; `keymap.changed` публикуется, только если после перечтения изменились записи файла или проблема файла. Рецепт тот же, что у `PluginWatcher` (`src/roost/plugin_watcher.hpp`): подпись пути — размер, время изменения и время смены метаданных, а не время доступа. Каталога конфига может не быть до первой записи документа: тогда слежение стоит на ближайшем существующем каталоге выше, и его событие переводит слежение на файл.
- Файл не JSON, не массив или больше 1 МиБ: действует прежняя таблица, и проблема видна пользователю. Это исключение из правила §8 «неразборный файл — ошибка»: файл правят руками, и опечатка не должна сбрасывать клавиши. При старте прежней таблицы нет, тогда действуют одни вклады. Битая запись (неразборная клавиша, неизвестная команда, `when` не строкой, клавиша без модификатора и без `when`, `Cmd` на Linux) пропускается с проблемой, остальные действуют.

Тексты проблем (`keymap.get` и `keymap.changed` отдают их строками вместе с проблемами вкладов, §5):

- файл: `keymap.json is ignored: <причина>`, причина — `it is not JSON: <текст разбора> at byte <смещение>`, `it is not an array`, `it is over 1 MiB` или `cannot read it: <текст ОС>`; при наличии прежней версии дальше `; the version before it stays`. Файл ровно в 1 МиБ читается.
- запись: `keymap.json entry <номер с 0> is ignored: <причина>`, причина — `it is not an object`, `it has neither "key" nor "mac"`, `"mac" is null and there is no "key": nothing to bind`, `"key" is not a string` (так же `mac`, `when`), `"command" is neither a string nor null`, `no plugin has the command <id>`, сообщение разбора клавиши или `<клавиша> has no Cmd, Ctrl or Alt: without "when" it would take the text typed into any panel`. Записи для другой платформы (`mac` на Linux) молча не действуют.
- `source` записи таблицы — `user` для файла, иначе id плагина.
- Окно показывает проблемы таблицы в полосе проблем (`Roost.keymapProblems`, после проблем `roostd` и перед проблемами шрифтов) и пишет `qWarning` каждую новую проблему `keymap.json`, которой не было в прежнем списке (после потери связи список пуст, так что при переподключении они пишутся снова); проблемы клавиш вкладов `roostd` пишет в свой лог сам, поэтому, если платформа окна не совпадает с платформой `roostd`, конфликты клавиш вкладов для платформы окна видны в полосе, но в лог окна не попадают; без таблицы список пуст. Текст, который уже есть среди проблем плагинов (`plugins.list` держит проблемы клавиш вкладов платформы демона), второй раз не добавляется.

Цена: JSON без комментариев, `QJsonDocument` их не принимает. Пояснить запись или временно закомментировать её нельзя; чтобы временно снять клавишу, запись удаляют. Альтернативы и причины отказа — ADR 014.
