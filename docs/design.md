# Архитектура roost

Решения и их цена. Фактура, на которой они основаны, — в [prior-art.md](prior-art.md); здесь только выводы и обоснования.

---

## 1. Цели и границы

Четыре цели, в порядке приоритета:

1. Отзывчивость. Список сессий, хоткеи и панели не теряют кадров, пока терминалы льют вывод. Переход к недавней сессии — один кадр.
2. Плагины со старта. Каждая фича, включая встроенные, — плагин на публичном API, и её можно заменить целиком.
3. Модульный UI. Плагины добавляют панели; пользователь расставляет их и связывает выходы одной панели со входами другой.
4. Модульные агенты. Сначала Claude Code, потом Codex, OpenCode и агенты по ACP через тот же интерфейс адаптера.

Критерий готовности v1 одной строкой: **все фоновые сессии Claude видны без ручных действий, переход к тёплой сессии укладывается в кадр, а список отвечает на хоткеи, пока соседний терминал льёт 1 МБ/с.**

Не-цели v1, названные явно: песочница для плагинов, визуальный редактор связей, Windows, стабильный API плагинов, свой чат поверх SDK агента.

## 2. Компоненты

```
┌──────────────── roost (Qt Quick, C++) ─────────────────┐
│ Оболочка: раскладка, палитра команд, keymap             │
│ Панели плагинов (QML): список сессий, терминал, PR      │
│ TerminalItem (QQuickItem над libghostty-vt)             │
│ RPC-клиент  <->  QML-синглтоны API (Roost.*)            │
└───────────────────────────┬────────────────────────────┘
                            │ unix-сокет: JSON-RPC 2.0 + кадры PTY (§4)
┌───────────────────────────┴─── roostd (QtCore, QtNetwork) ┐
│ Адаптеры агентов │ Пул PTY  │ Бэкенды плагинов (процессы)│
│ Шина событий     │ Хранилище (JSON на плагин)            │
│ libghostty-vt: экран каждой тёплой сессии                │
└───────────────────────────────────────────────────────────┘
```

| Процесс | Владеет | Переживает |
|---|---|---|
| `roost` | окном, рендером, QML плагинов | — |
| `roostd` | PTY, адаптерами, бэкендами плагинов, состоянием | перезапуск и обновление окна |
| агент (`claude --bg` и т. п.) | своей сессией | перезапуск `roostd`, если у агента свой демон |

Зачем отдельный демон:

- PTY и адаптеры живут дольше окна: перезапуск `roost` не рвёт тёплые attach.
- Агенты без своего демона (TUI Codex, Gemini) живут в PTY `roostd`.
- Удалённый хост позже запускает тот же `roostd`, окно подключается через ssh.

Оба процесса на C++ и в одной сборке. `roostd` линкует QtCore (цикл событий, `QProcess`, `QSocketNotifier`) и QtNetwork (`QLocalServer`). GUI в нём нет.

Инвариант: **окно не держит состояния, которое нельзя восстановить из `roostd`.** Раскладка, связи и настройки плагинов лежат в хранилище демона.

## 3. Терминал

### Разбор и состояние экрана

libghostty-vt (C API, MIT) разбирает VT-поток и хранит экран. Рендера и PTY в нём нет. Собирается из исходников через CMake `FetchContent` на теге `vt-1.0.1`, цель `ghostty-vt-static`; нужен Zig ≥ 0.17.0.

Терминал libghostty-vt не потокобезопасен: все операции над одним терминалом сериализует вызывающий (prior-art §2.2). Владелец терминала в окне — `TerminalSession` (`src/terminal/`), по одной на тёплую сессию: терминал, render state и мьютекс. `TerminalItem` только показывает одну из них. Схема потоков в окне:

| Поток | Что делает | Держит лок терминала |
|---|---|---|
| ввода-вывода, один на окно | читает сокет, разбирает кадры, кормит терминалы всех своих сессий | да, на время записи куска |
| GUI | события клавиатуры и мыши; перед кодированием синхронизирует режимы энкодера с терминалом (`ghostty_key_encoder_set_from_terminal`) | да, коротко, только на синхронизацию |
| рендера Qt Quick | под локом `ghostty_render_state_begin_update`, без лока `end_update` и перестройка грязных строк в `updatePaintNode` | да, только на begin |

Render state читается только после `end_update` (prior-art §2.2), поэтому обе фазы делает один поток — поток рендера, а не тот, кто кормит терминал. Под локом нужна только фаза begin; фаза end работает с памятью render state и безопасна, пока поток ввода-вывода пишет в терминал.

Все вызовы libghostty-vt идут через методы `TerminalSession`, которые в отладочной сборке проверяют, что лок взят. TSan не видит доступов внутри библиотеки, собранной Zig без инструментации, и эта проверка его заменяет.

В демоне поток один, локов нет. На терминалах демона включён `GHOSTTY_TERMINAL_OPT_CONTINUATION_MAX_BYTES`: PTY читается кусками, которые рвут последовательности посередине, а без этой опции снимок терминала не в ground-состоянии не кодируется (`snapshot.h`, prior-art §2.3).

GUI-поток не разбирает вывод никогда. Qt Quick по умолчанию рендерит в отдельном потоке на macOS с Metal и на Linux, кроме Mesa llvmpipe (prior-art §5.1); на llvmpipe рендер уходит в GUI-поток, и это деградация, а не поломка.

### Тёплые сессии и снимок

Холодный `claude attach` отдаёт первый байт через 133–151 мс, полный кадр — через 136–155 мс в тёплом прогоне и до 922 мс в первом (prior-art §1.3). Attach при каждом переключении не годится.

Экран терминала — результат всего потока байт с начала attach: TUI агента не перерисовывает экран целиком, а двигает курсор и меняет отдельные ячейки. Подключиться к середине потока нельзя, нужно текущее состояние экрана.

| Где | Что держит | Зачем |
|---|---|---|
| `roostd` | PTY и терминал libghostty-vt на каждую тёплую сессию | переживает окно; отвечает на запросы терминала (DA, CPR), когда окна нет; источник снимка |
| `roost` | свой терминал libghostty-vt на каждую тёплую сессию, кормится потоком в фоне | переключение без снимка и без attach — только отрисовка |

- Тёплых сессий N, по умолчанию 4, вытеснение по давности просмотра. Вытесненная сессия закрывает attach и в демоне, и в окне.
- Переход к тёплой сессии — смена терминала, который рисует `TerminalItem`, один кадр. Переход к холодной — attach, 130–155 мс, с индикатором в панели.
- Отвечает на запросы терминала только демон. Терминал окна в PTY не пишет, иначе агент получит два ответа на один запрос.

Снимок (`snapshot.h`, бинарный формат) нужен в трёх случаях: старт или перезапуск окна при живом `roostd`, первое открытие в окне сессии, которая уже тёплая в демоне, и подключение к удалённому `roostd`. Демон однопоточный: снимок и подписка окна на поток канала делаются в одном проходе цикла событий, поэтому между снимком и первым байтом потока нет ни пропуска, ни повтора.

Терминал с обеих сторон — `src/core/vt_terminal.hpp`. Поток режется где угодно, в том числе посреди escape-последовательности или символа UTF-8: терминал демона помнит недописанный хвост до 1 МиБ, снимок его несёт, а восстановленный терминал окна дописывает следующими байтами потока. Снимок посреди более длинной последовательности не снимается, пока поток её не закончит. На запросы отвечает только терминал с обработчиком ответов, а восстановленный из снимка создаётся без него. Байты снимка не канонические: после декодирования библиотека заново назначает id стилей и ссылок. Поэтому два терминала сравнивают по `Dump()` — VT-последовательностям, которые воссоздают активный экран со скроллбеком, режимами и курсором; заголовок, цвета из OSC и сохранённый курсор в дамп не попадают, хотя снимок их несёт. Размер терминала — от 1 до 2000 колонок и строк: память под ячейки берётся сразу.

Снимок декодируется только от своего `roostd`, то есть от процесса того же пользователя. Декодер libghostty-vt 1.0.1 не рассчитан на враждебный ввод: на искажённом снимке сборка ReleaseSafe падает паникой, а развёрнутый снимок может занять гигабайты. Подключение к удалённому `roostd` потребует проверки целостности снимка и аллокатора с бюджетом памяти для декодера.

Цена:
- каждый тёплый attach стоит 59–126 МБ RSS (prior-art §1.3);
- вывод разбирается дважды, в демоне и в окне; память терминала libghostty-vt в окне не мерилась — замер в M3;
- формат снимка не входит в гарантии ABI libghostty-vt (prior-art §2.3), поэтому окно и демон собираются с одним тегом библиотеки; рукопожатие сверяет его (§4).

### PTY

Программа в PTY (`src/core/pty.hpp`) запускается в новой сессии, и PTY — её управляющий терминал, stdin, stdout и stderr. `TERM=xterm-256color`, если команда адаптера не задала другой. Закрытие PTY шлёт программе SIGHUP; если она не вышла за секунду, SIGKILL получает вся её группа процессов, вместе с тем, что она запустила и что тоже не реагирует на SIGHUP. Ввод до перехода программы в raw-режим обрабатывает драйвер терминала, как в любом эмуляторе: эхо, ^C превращается в SIGINT. Вывод, который программа успела записать до выхода, доходит до читателя раньше события о выходе.

### Ввод

Клавиши и мышь кодируются энкодерами libghostty-vt (`key.h`, `mouse.h`) с учётом режимов терминала и уходят в PTY через `roostd` кадром ввода (§4).

### Размер

- Размер PTY задаёт панель, которая последней получила фокус или изменила размер среди панелей, показывающих сессию. Окно шлёт `session.resize(channel, cols, rows)`; демон делает `TIOCSWINSZ` и меняет размер своего терминала, окно — своего.
- Другие панели той же сессии рисуют сетку как есть, с обрезкой или полями, и PTY не трогают — иначе две панели разного размера дёргали бы TUI по кругу.
- Без окна PTY сохраняет последний размер.

## 4. Протокол окна и демона

Один unix-сокет на пользователя: `ROOST_SOCKET`, иначе `$XDG_RUNTIME_DIR/roost/roostd.sock`, иначе `roost-<uid>/roostd.sock` во временном каталоге (`$TMPDIR` на macOS). Каталог сокета демон создаёт с правами 0700. Существующий каталог должен принадлежать пользователю и быть закрыт для остальных, иначе демон не стартует: чужие права демон не меняет. Рядом с сокетом лежит `<сокет>.lock`. Второй демон на тот же сокет выходит с ошибкой, а сокет умершего демона заменяется. Сервер — `src/roostd/server.hpp`, клиент — `src/core/rpc_client.hpp`.

Кадр: `u32 длина | u8 вид | тело`. Длина — big-endian и считает байты после себя (вид и тело), так что она не меньше 1. Длина больше 16 МиБ, нулевая длина и неизвестный вид — ошибка протокола: соединение закрывается, потому что границам кадров в таком потоке верить нельзя. Кодек — `src/core/frame.hpp`; в тело он не заглядывает, номер канала проверяет получатель.

| Вид | Тело | Назначение |
|---|---|---|
| 0 | JSON-RPC 2.0 (UTF-8) | запросы, ответы, уведомления |
| 1 | `u32 канал`, байты | вывод PTY демон → окно |
| 2 | `u32 канал`, байты | ввод окно → демон |
| 3 | `u32 канал`, снимок | снимок терминала при открытии |

Тело вида 0 — запрос, уведомление или батч по спецификации JSON-RPC 2.0, диспетчер с таблицей методов — `src/core/rpc.hpp`. Обработчик отвечает асинхронно, поэтому ответы приходят не обязательно в порядке запросов: клиент сопоставляет их по `id`.

Первый запрос — `hello` с версией протокола и версией libghostty-vt (`build_info.h`). Окно и демон ставятся одним пакетом, так что расхождение бывает только после обновления, пока работает старый демон. Тогда демон отказывает в рукопожатии, клиент закрывает соединение, а окно предлагает перезапустить `roostd`: тёплые attach теряются, сами сессии живут в демоне агента.

| Метод | Параметры | Результат |
|---|---|---|
| `hello` | `{protocol, ghosttyVt}` | `{protocol, ghosttyVt, roostd}` |
| `bus.subscribe` | `{pattern}` | `{subscription}` |
| `bus.unsubscribe` | `{subscription}` | `null` |
| `bus.publish` | `{name, payload?}` | `null` |
| `commands.run` | `{command, args?}` | ответ бэкенда плагина, которому принадлежит команда |
| `sessions.list` | — | `{sessions, unavailable}`: сессии всех агентов и `{agent, reason}` для агентов, чей адаптер не ответил списком |

События шины приходят уведомлениями `bus.event {subscription, name, payload}`. Подписки соединения снимаются вместе с ним, а снять чужую подписку нельзя. Событие, которое не поместится в кадр, `bus.publish` отвергает с `InvalidParams`, а не теряет у подписчиков.

`commands.run` передаёт бэкенду владельца тот же запрос (`src/roostd/plugins.hpp`). Неизвестная команда — `InvalidParams`, плагин без бэкенда или с лежащим бэкендом — -32003. О бэкендах демон сам публикует события `plugin.backendCrashed {plugin, reason, restartInMs}` и `plugin.backendGaveUp {plugin, reason}`.

`sessions.list` опрашивает адаптеры всех агентов разом (§7) и отдаёт сессии агент за агентом в порядке загрузки плагинов. Сессия — `{agent, id, title, cwd, state, startedAt?}`, `startedAt` в миллисекундах от эпохи. Упавший или ответивший не по схеме адаптер не валит список, а попадает в `unavailable` с причиной. Таймаута нет: зависший адаптер держит ответ, пока его бэкенд не остановят, и каждый новый `sessions.list` добавляет ещё один ждущий запрос к нему. Список, который не помещается в кадр, — `InternalError`, а не обрыв соединения. Смену состояния сессии демон публикует событием `session.stateChanged` с сессией в том же виде; событие больше кадра отбрасывается с записью в лог.

По SIGTERM и SIGINT демон останавливает бэкенды и убирает сокет и lock-файл. Запрос, который ждал бэкенд, ответа не получит: клиент увидит обрыв соединения.

Коды ошибок демона лежат в диапазоне, который JSON-RPC оставляет серверам (`src/core/protocol.hpp`):

| Код | Когда |
|---|---|
| -32000 | метод вызван до успешного `hello` |
| -32001 | `hello` с другой версией протокола или libghostty-vt; в `data` версии демона |
| -32002 | на стороне клиента: соединение потеряно, запрос не получит ответа |
| -32003 | бэкенд плагина не запущен или завершился, не ответив |

Соединение закрывается, если сломан поток кадров, пришёл кадр канала (до M2 каналов нет) или клиент не читает и у демона скопилось больше 64 МиБ неотправленного.

Канал сессии: `session.open(id)` возвращает номер канала и, если сессия уже тёплая, присылает снимок (вид 3); дальше идут кадры вывода (вид 1). `session.input` не нужен — ввод идёт кадрами вида 2. `session.resize` и `session.close` — запросы JSON-RPC.

Почему не чистый JSON-RPC: байты PTY в JSON — это base64 плюс экранирование, +33 % к объёму и разбор строки в GUI-потоке. Цена отказа: сокет не отладить голым `socat` и `jq`; лечится командой `roostd --dump`, которая печатает кадры читаемо.

`roostd --dump` подключается к работающему демону, здоровается, подписывается на все события шины и печатает по строке на каждый пришедший кадр (`src/roostd/dump.hpp`):

```
rpc {"jsonrpc":"2.0","method":"bus.event","params":{...}}
output channel 7, 8 bytes "ls\r\n\x1b[0m"
```

Тело кадра RPC печатается как пришло, только переводы строк и табуляции заменяются пробелами; если тело не одно JSON-значение — экранированной строкой с пометкой `(not JSON)`. У кадра канала печатается номер канала, размер и первые 64 байта в кавычках; управляющие и не-ASCII байты экранируются как `\xNN`, а обрезанное превью кончается на `...`. Команда завершается с кодом 0, когда демон закрыл соединение или читатель вывода ушёл (`roostd --dump | head`), и с кодом 1, если подключиться не удалось, демон отказал в `hello` или подписке, поток кадров сломан или оборвался посреди кадра.

Бэкенды плагинов говорят с `roostd` чистым JSON-RPC 2.0 по stdio, построчно: им байты PTY не нужны.

## 5. Плагины

Плагин — каталог:

```
plugins/claude/
  plugin.json
  qml/            # UI: панели, страницы настроек (необязательно)
  backend/        # любой исполняемый файл с JSON-RPC по stdio (необязательно)
```

`plugin.json`:

```json
{
  "id": "claude",
  "version": "0.1.0",
  "api": "0",
  "backend": { "command": ["backend/claude-adapter"] },
  "contributes": {
    "agents": [{ "id": "claude", "capabilities": ["backgroundDaemon", "nativeTuiAttach"] }],
    "panels": [{ "id": "claude.transcript", "qml": "qml/Transcript.qml",
                 "inputs": { "session": "SessionRef" }, "outputs": {} }],
    "commands": [{ "id": "claude.newSession", "title": "New Claude session" }],
    "keybindings": [{ "command": "claude.newSession", "key": "Ctrl+N" }],
    "settings": "qml/Settings.qml"
  }
}
```

| Часть | Как работает | Где выполняется |
|---|---|---|
| UI | QML с диска через `QQmlComponent`, без шага компиляции; в режиме разработки перезагружается при изменении файла | GUI-поток окна, рендер — поток рендера |
| API для QML | C++-объекты как QML-синглтоны: `Roost.sessions` (модель), `Roost.commands.run(id, args)`, `Roost.send(sessionId, text)`, `Roost.store`, `Roost.bus`; `TerminalItem` — зарегистрированный QML-тип | GUI-поток |
| Лёгкая логика | JavaScript в QML | GUI-поток |
| Тяжёлая логика и состояние | бэкенд-процесс плагина, любой язык | отдельный процесс, запускает `roostd` |
| Нативный C++ | только встроенные плагины из той же сборки | процесс `roost` или `roostd` |

- Встроенные фичи живут в `plugins/` и ходят через тот же API: список сессий с категориями, пинами, архивом и непрочитанными; терминальная панель; уведомления; PR по worktree; keep-awake; адаптер Claude. Заменить фичу — выключить встроенный плагин и поставить другой с теми же вкладами.
- Конфликт вкладов (две команды с одним id, два хоткея на одну клавишу) решается порядком загрузки плюс явным переопределением пользователя; конфликт виден в палитре команд.
- API версии `0` нестабилен, пока на нём не заработают 2–3 настоящих плагина.
- Поиск: каталоги из `ROOST_PLUGINS_PATH` (через `:`, только абсолютные пути), затем `<каталог состояния>/plugins`; каталог, названный дважды, просматривается один раз. В каждом — подкаталоги с `plugin.json`, по имени с учётом регистра: заглавные раньше строчных. Порядок поиска и есть порядок загрузки. Второй плагин с тем же `id` не загружается.
- Манифест проверяется при загрузке (`src/roostd/manifest.hpp`): `api` совпадает с API демона, программа бэкенда и `settings` — пути внутри каталога плагина (проверка по тексту пути, симлинки не раскрываются: код плагина и так работает от имени пользователя), хоткей назначен на команду того же плагина, у плагина с агентами есть бэкенд. Id агента — как id плагина; агент, объявленный вторым плагином, остаётся за первым. Хоткей команды, проигравшей конфликт, тоже не действует. Неизвестные ключи игнорируются. Плагин с битым манифестом не загружается, а остальные загружаются; отказ и каждый проигравший конфликт сохраняются как проблема для пользователя.
- Бэкенд (`src/roostd/backend.hpp`) запускается в каталоге плагина, в своей сессии: Ctrl-C в терминале демона до него не доходит. Протокол — JSON-RPC 2.0, одно компактное сообщение на строку в stdin и stdout; stderr бэкенда идёт в stderr демона. Демон шлёт запросы и ждёт ответов без таймаута; уведомления бэкенда принимает, а на запрос от бэкенда пока отвечает `MethodNotFound`. Закрытый stdin значит «завершись»: через секунду после этого процесс убивается.
- Бэкенд упал, если сам завершился, не запустился или нарушил протокол: строка не JSON-RPC, ответ на чужой id, ответ без `result` и `error`, `error` не объектом, строка длиннее 16 МиБ. Нарушителя демон убивает. Ждущие запросы получают -32003, демон перезапускает бэкенд через 0,5 с, и с каждым падением подряд пауза удваивается, до 30 с. После пятого перезапуска подряд бэкенд остаётся лежать. Минута работы без падений обнуляет счёт.

Цена: JavaScript плагина выполняется в GUI-потоке, и небрежный плагин может подвесить окно. Смягчение — бэкенд-процессы для тяжёлого и оверлей времени кадра в режиме разработки, который называет медленную панель.

## 6. Панели и связи

- Раскладка — дерево сплитов и стопок вкладок в JSON. Лист хранит id панели, её тип и таблицу связей.
- Тип панели объявляет типизированные входы и выходы (`session: SessionRef`, `selection: SessionRef[]`). В QML это обычные свойства.
- Связь соединяет выход одной панели со входом другой и применяется как привязка свойства QML, например `terminal.session = Qt.binding(() => list.selected)`. Связи хранятся в JSON раскладки.
- Пример: список → `selected` → терминал и панель PR. Две пары «список + терминал» в одном окне независимы.
- Связи редактируются из контекстного меню панели; визуального редактора в v1 нет.

Цена: связь — это привязка внутри одного QML-движка, поэтому связывать панели разных окон нельзя. Межоконные связи потребовали бы шины через `roostd`; отложено, пока окно одно.

## 7. Адаптеры агентов

```cpp
struct AgentAdapter {
    virtual Capabilities GetCapabilities() const = 0;   // backgroundDaemon, nativeTuiAttach, structuredStream
    virtual QFuture<std::vector<Session>> ListSessions() = 0;
    virtual QFuture<SessionRef> Start(const StartOptions&) = 0;
    virtual QFuture<void> Stop(const SessionRef&) = 0;
    virtual QFuture<std::optional<PtySpec>> AttachCommand(const SessionRef&) = 0;  // roostd запускает в PTY
    virtual QFuture<void> Send(const SessionRef&, const QString& text) = 0;
    virtual QFuture<void> AnswerPermission(const SessionRef&, const QString& requestId, const PermissionAnswer&) = 0;
    // события: StateChanged, PermissionRequested, TitleChanged, Usage
};
```

- Асинхронность — `QFuture<T>` из QtCore (`QPromise`, `then`): без корутин и без новой зависимости.
- Внешние адаптеры работают как бэкенды плагинов; `roostd` оборачивает их мостом, который реализует этот интерфейс поверх JSON-RPC. Адаптер Claude — встроенный плагин на том же протоколе.
- Мост — `src/roostd/adapter_bridge.hpp`, по одному на агента. Демон зовёт бэкенд `agent.listSessions {agent}` → `[{id, state, title?, cwd?, startedAt?}]` и `agent.attachCommand {agent, session}` → `{program, args?, cwd?, env?}` или `null`, если к сессии не подключиться; `env` — объект `{ИМЯ: значение}`. Бэкенд сам шлёт уведомление `session.stateChanged {agent, session}` о своих агентах. Ответ не по схеме — `InternalError` с причиной; уведомление о чужом агенте или не по схеме демон пишет в лог и отбрасывает. Пока реализованы только эти три части интерфейса. Ошибка адаптера без `message` попадает в `unavailable` как `error <code>`. Агент, объявленный плагином дважды, получает один мост.
- Общие состояния: `working`, `blocked` (ждёт человека), `idle`, `done`, `failed`.

| Агент | Сессии и состояние | Видимый TUI | Свой демон |
|---|---|---|---|
| Claude Code | `claude agents --json`, хуки | `claude attach` в PTY | да, `--bg` |
| Codex | `codex app-server`: `thread/list` и т. п. | `codex resume` в PTY `roostd` | нет |
| OpenCode | `opencode serve`: HTTP + SSE | TUI в PTY `roostd` | да |
| Gemini и др. | хуки, ACP | TUI в PTY `roostd` | нет |

Протоколы — prior-art §4. Установка хуков агента (`Notification` у Claude Code, `~/.codex/hooks.json`) меняет конфиг чужого инструмента, поэтому делается только по явному согласию в UI (ADR 012).

## 8. Состояние и миграция

- `roostd` хранит состояние в JSON под `~/.config/roost/`, отдельное пространство имён на плагин. Запись атомарная: временный файл и `rename`.
- Каталог: `ROOST_CONFIG`, иначе `$XDG_CONFIG_HOME/roost`, иначе `~/.config/roost`. Без `HOME` и без двух переменных выше демон не стартует, а не пишет в корень. Созданный демоном каталог закрыт правами 0700. Файл плагина — `<id>.json` с правами 0600. В id только строчные латинские буквы, цифры, `.`, `_` и `-`, первым символом буква или цифра: на нечувствительной к регистру ФС macOS `Claude` и `claude` иначе стали бы одним файлом. Файл, который не разбирается, — ошибка, а не пустой документ.
- Первый запуск импортирует `~/.config/cc-fleet/{categories,archive,colors,names,seen,settings}.json`. Исходные файлы не меняются.
- Из cc-fleet переезжает логика: категории, пины, архив, имена, цвета, непрочитанные, переходы и тексты уведомлений, поиск PR по worktree, keep-awake. Тесты cc-fleet (`test_pins`, `test_tree`, `test_fold_cursor`, `test_notify`, `test_pulls`, `test_awake`, `test_subagents`, `test_launched`, `test_title`) переносятся в Qt Test случай за случаем.

## 9. Бюджеты

| Что | Бюджет | Откуда число |
|---|---|---|
| кадр окна | 16,7 мс при 60 Гц | частота экрана |
| работа GUI-потока на кадр | ≤ 4 мс | запас под JS плагинов и раскладку |
| переход к тёплой сессии | 1 кадр | терминал уже в окне (§3) |
| переход к холодной сессии | ≤ 200 мс | attach 133–155 мс; окно подписано с первого байта, снимок не нужен |
| тёплых attach по умолчанию | 4 | 59–126 МБ RSS каждый |

Бюджеты проверяются тестом в CI с синтетическим потоком 1 МБ/с в соседние терминалы. Платформа `offscreen` не даёт RHI, и Qt Quick переходит на программный рендер, у которого поток рендера по умолчанию выключен (prior-art §5.1). Поэтому тест запускается с `QSG_RENDER_LOOP=threaded` и мерит время GUI-потока отдельно от рендера. Цифры на программном рендере не равны цифрам на экране: тест ловит регрессии, а не доказывает 60 Гц.

## 12. Доверие

- Плагины без песочницы. Плагин видит всё, что отдаёт API, включая транскрипты, и может печатать в сессии. Ставить только доверенные.
- Сокет `roostd` — только для своего пользователя: каталог 0700, на Linux проверка `SO_PEERCRED`, на macOS — `getpeereid`.
- Хуки агентов и любые правки чужих конфигов — только по явному согласию в UI.

## 13. План реализации

Работа идёт этапами. **После каждого — остановка и ожидание отмашки**; следующий этап не начинается автоматически. Каждый этап — стек небольших самодостаточных коммитов; критерий готовности прогоняется и показывается целиком.

| Этап | Содержание | Критерий готовности |
|---|---|---|
| **M0** | каркас: CMake, пресеты, Qt, libghostty-vt, пустые `roost` и `roostd`, CI с гейтами | три пресета зелёные на macOS; `roost --smoke` выходит с 0 под `offscreen`; гейт нейминга ловит намеренное нарушение в каждом из двух стилей; Qt подключён динамически |
| **M1** | `roostd`: кадры, JSON-RPC, шина, хранилище, загрузчик плагинов | тестовый клиент через сокет вызывает команду бэкенда-фикстуры и получает ответ; упавший бэкенд перезапускается и о падении приходит событие; разбиение потока на любые куски даёт те же кадры |
| **M2** | PTY, тёплый пул, каналы сессий, адаптер Claude | список сессий совпадает с `claude agents --json --all`; терминал демона, накормленный записанным потоком, совпадает с эталонным терминалом на том же потоке; снимок после кодирования и декодирования совпадает с исходным; запросы фейкового TUI получают ровно один ответ |
| **M3** | `TerminalSession`, рендер, `TerminalItem` | через настоящий `roostd` ввод доходит до фейкового TUI и его эхо отрисовано; изменение размера доходит до PTY; GUI-поток тратит ≤ 4 мс на кадр, пока 10 терминалов получают по 1 МБ/с; `tsan` и проверки лока чистые |
| **M4** | окно и встроенные плагины: список сессий, терминал, импорт cc-fleet. **Рабочий продукт** | у каждой клавиши cc-fleet есть эквивалент; перенесённые тесты cc-fleet зелёные; перезапуск окна сохраняет состояние и тёплые сессии; переход к тёплой сессии — один кадр |
| **M5** | раскладка панелей со связями, keymap, палитра команд | две пары «список + терминал» независимы; раскладка переживает перезапуск; встроенный список сессий заменяется плагином-фикстурой без правок ядра |
| **M6** | уведомления, PR, keep-awake | перенесённые тесты зелёные на macOS и Linux; уведомление о переходе в `blocked` приходит не позже одного опроса |
| **M7** | упаковка `.dmg` и AppImage | AppImage запускается на чистом `ubuntu-24.04` без установленного Qt; `.app` берёт Qt из бандла; тексты лицензий внутри обоих пакетов |

**M4 — уже полноценный продукт**: заменяет cc-fleet в ежедневной работе. M5–M7 расширяют его, а не доделывают.

### M0: каркас

Подготовка: на маке `brew install qt zig` (Qt 6.12.0, Zig 0.17.1). Linux проверяется в CI; локально — в Lima VM, если CI недостаточно.

Шаги:

1. `CMakeLists.txt`, `CMakePresets.json` с пресетами `dev`, `asan-ubsan`, `release` (Ninja, `CMAKE_EXPORT_COMPILE_COMMANDS`). CMake падает на компиляторе, отличном от clang.
2. `cmake/ghostty.cmake`: `FetchContent_Declare(ghostty ... GIT_TAG vt-1.0.1)` (коммит `108cacb`), цель `ghostty-vt-static`. Нет Zig в `PATH` — понятная ошибка конфигурации.
3. `src/core/` — статическая библиотека `roost_core`, пока с одной функцией: версия roost и libghostty-vt.
4. `src/roostd/main.cpp` — `QCoreApplication`, `--version`.
5. `src/roost/main.cpp` — `QGuiApplication` и пустое окно на QML; `--smoke` закрывает окно после первого кадра (`QQuickWindow::frameSwapped`).
6. `src/qml_api/` с `.clang-tidy` из ADR 011.
7. `tests/`: Qt Test — терминал libghostty-vt получает `hello\r\n\x1b[31mred`, formatter отдаёт `hello\nred`; запуск `roost --smoke` под `QT_QPA_PLATFORM=offscreen`.
8. `tests/gates/naming/core/` — метод в camelCase; `tests/gates/naming/qml_api/` — метод в PascalCase и симлинк `.clang-tidy` на `src/qml_api/.clang-tidy` (стиль берётся по каталогу файла, поэтому фикстуре нужен тот же конфиг, а не копия). Гейт запускает `clang-tidy` на обоих файлах с флагами компиляции после `--` и требует ненулевой код на каждом; `WarningsAsErrors` наследуется из корня.
9. `.github/workflows/ci.yml`: сборка на `macos-15` (arm64); Linux добавляется, когда решён вопрос «какой Linux» (§14). Qt одной версией через `install-qt-action`, Zig через `setup-zig`; джобы `test` (три пресета), `format` (`clang-format`, `qmlformat`), `tidy` (`clang-tidy-20`), `gates`. Проверка динамической линковки Qt: `tools/check_qt_dynamic.sh` (`otool -L`, на Linux `ldd`).

CI требует репозиторий на GitHub; до его появления критерий M0 прогоняется локально на маке, а Linux-часть ждёт.

### M1: `roostd`

1. `src/core/frame.{hpp,cpp}` — кодек кадров §4 без ввода-вывода: на вход байты, на выход кадры; предел длины кадра, ошибка на превышение.
2. `src/core/rpc.{hpp,cpp}` — JSON-RPC 2.0: запросы, ответы, уведомления, коды ошибок спецификации; таблица методов.
3. `src/core/bus.{hpp,cpp}` — шина событий с подпиской по префиксу имени (`session.*`).
4. `src/core/store.{hpp,cpp}` — JSON на плагин в `~/.config/roost/<plugin>.json`, запись через `QSaveFile` (временный файл и `rename`); каталог переопределяется `ROOST_CONFIG`, тесты всегда задают его.
5. `src/roostd/server.{hpp,cpp}` — `QLocalServer`, каталог сокета 0700, проверка UID пира (`SO_PEERCRED` / `getpeereid`), рукопожатие `hello`.
6. `src/roostd/plugins.{hpp,cpp}` — поиск каталогов плагинов, разбор и проверка `plugin.json`, реестр вкладов с обнаружением конфликтов, запуск бэкендов через `QProcess` (JSON-RPC построчно по stdio), перезапуск с экспоненциальной задержкой и пределом попыток.
7. `src/core/rpc_client.{hpp,cpp}` — клиент сокета: рукопожатие, запросы с `QFuture`, подписки на уведомления и каналы. Им пользуются окно и тесты; `roostd --dump` читает сокет сам, чтобы печатать кадры как есть.
8. `roostd --dump` — подключается к сокету и печатает кадры читаемо.

Тесты: кодек кадров на всех разбиениях потока; ошибки JSON-RPC по спецификации; хранилище не оставляет полузаписанного файла; загрузчик на плагинах-фикстурах, бэкенд — маленький C++-хелпер из `tests/helpers/`, без Python.

### M2: PTY, тёплый пул, каналы сессий, адаптер Claude

1. `src/core/pty.{hpp,cpp}` — `openpty`, `fork`/`exec`, `TIOCSWINSZ`, чтение через `QSocketNotifier`, сбор завершившихся детей.
2. `src/roostd/warm_pool.{hpp,cpp}` — канал на тёплую сессию: PTY плюс терминал libghostty-vt с continuation tracking; ответы на запросы терминала через колбэк записи в PTY; вытеснение по давности просмотра, N из настроек.
3. `session.open`, `session.resize`, `session.close`, кадры ввода и вывода (§4); снимок и подписка на канал в одном проходе цикла событий (§3).
4. `src/roostd/adapter_bridge.{hpp,cpp}` — `AgentAdapter` поверх JSON-RPC к бэкенду плагина.
5. `plugins/claude/` — бэкенд `claude-adapter` на C++ и QtCore: опрос `claude agents --json --all` раз в 3 с (как `POLL_SEC` в cc-fleet), разбор в `Session`, события `session.stateChanged`; `AttachCommand` — `claude attach <id>`.

Тесты: адаптер на записанных ответах `claude agents --json` в `tests/fixtures/`; терминал демона против эталонного терминала на одном записанном потоке, поток режется на куски в случайных местах; снимок туда и обратно; PTY и пул на фейковом TUI из `tests/helpers/` (рисует адресацией курсора, шлёт DA1 и CPR); тест на настоящем `claude` только при `ROOST_REAL_CLAUDE=1`, без ввода в сессии. Замер RSS тёплого attach записывается в prior-art.

### M3: `TerminalSession` и `TerminalItem`

1. `src/terminal/terminal_session.{hpp,cpp}` — терминал, render state, мьютекс; все вызовы libghostty-vt через методы с проверкой лока (§3).
2. `src/terminal/io_thread.{hpp,cpp}` — один поток на окно: `rpc_client` из M1, разбор кадров, запись в терминалы сессий.
3. `src/terminal/renderer.{hpp,cpp}` — `begin_update` под локом, `end_update`, перестройка грязных строк. Строки рисуются через `QSGTextNode` (Qt 6.7+, `QQuickWindow::createTextNode()`): шейпинг и замена шрифтов из коробки. Если бюджет кадра не сходится — атлас глифов; решение по замеру, оба варианта на одном бенчмарке.
4. `src/qml_api/terminal_item.{hpp,cpp}` — `QQuickItem`, показывает одну `TerminalSession`, `updatePaintNode` отдаёт рендереру.
5. Ввод: энкодеры клавиш и мыши, вставка с bracketed paste, выделение и копирование, прокрутка scrollback; `session.resize` (§3).
6. Режим разработки `roost --session <id>`: одна сессия на всё окно, без плагинов.
7. Пресет `tsan`. Замер памяти терминала libghostty-vt в окне при пустом и полном scrollback — в prior-art.

Тесты: таблица кодирования клавиш; содержимое ячеек после известного VT-потока (не скриншоты: шрифты в CI разные); сквозной тест окно → `roostd` → фейковый TUI: эхо ввода и размер PTY; бенчмарк кадра с `QSG_RENDER_LOOP=threaded` (§9). TUI Claude проверяется руками и в критерий не входит.

### ADR 001: окно на Qt Quick и C++

**Контекст.** Отзывчивость — первая цель (§1). Главный враг — разбор и рендер вывода терминалов в том же потоке, что и остальной UI. Вторая цель — UI плагинов, который грузится на лету без компиляции.

**Решение.** Qt Quick (QML) на C++: рендер в отдельном потоке, QML-плагины с диска, терминал — свой `QQuickItem` над libghostty-vt.

**Альтернативы.**

| Вариант | Почему отказ |
|---|---|
| Electron + xterm.js | разбор и рендер xterm.js в главном потоке renderer'а, терминалы на одной странице тормозят друг друга; около 16 WebGL-контекстов на страницу (prior-art §5.3) |
| Tauri | системный WebView: на Linux WebKitGTK с известными проблемами графики (prior-art §5.4); та же проблема главного потока xterm.js |
| GPUI (Rust) | API до 1.0; у расширений Zed нет своих панелей, UI плагинов пришлось бы строить с нуля (prior-art §5.4) |
| Dear ImGui | нет простоя без ввода из коробки, нет HarfBuzz и accessibility; нативные плагины ImHex привязаны к версии (prior-art §5.4) |
| Slint | лицензия без отчислений запрещает распространять приложение, которое «exposes the APIs» — плагины на `.slint` под это подпадают |
| RmlUi | на Wayland и X11 без IME и HiDPI, полноценно только через SDL |
| egui, iced | нет UI плагинов на лету |
| Go | нет зрелого GUI |

**Последствия.** Сборка тяжелее: Nheko на Qt Quick — 69 МБ против 25–45 МБ у приложений на ImGui и GPUI (prior-art §5.4) и тяжёлый тулчейн (moc, QML-движок). JavaScript плагинов выполняется в GUI-потоке (§5). Обязательства LGPLv3 (ADR 010).

### ADR 004: тёплые сессии в демоне и в окне, снимок только при подключении окна

**Контекст.** Холодный `claude attach` — 133–155 мс до полного кадра в лучшем случае, до 922 мс в первом прогоне (prior-art §1.3). Стек UI на это не влияет. Состояние экрана обязано пережить перезапуск окна (§2).

**Решение.** `roostd` держит N attach открытыми и хранит экран каждого в libghostty-vt. Окно держит свой терминал на каждую тёплую сессию и кормит его потоком в фоне. Бинарный снимок передаётся, только когда окно подключается к уже тёплой сессии (§3).

**Альтернативы.**

| Вариант | Почему отказ |
|---|---|
| attach при каждом переключении | 130–155 мс на переход, нарушает §1 |
| держать attach ко всем сессиям | 59–126 МБ RSS на attach; при 13 сессиях до 1,6 ГБ сверх самих агентов |
| терминал только в демоне, снимок на каждое переключение | связка окна и демона по формату снимка срабатывает на каждом переходе, а не изредка |
| терминал только в окне | состояние экрана умирает вместе с окном, нарушает инвариант §2 |
| проиграть окну весь вывод с начала attach | объём не ограничен |
| попросить TUI перерисоваться (resize, Ctrl-L) | зависит от агента, теряет scrollback, экран мигает |
| снимок как VT-поток через formatter | не зависит от формата снимка, но полнота восстановления (режимы, scrollback) не проверена; при расхождении версий проще перезапустить демон (§4) |

**Последствия.** Разбор вывода дважды. Окно и демон собираются с одним тегом libghostty-vt. Память растёт линейно с N в обоих процессах.

### ADR 005: плагин — QML и бэкенд-процесс

**Контекст.** Плагину нужны свой UI и своя логика. UI должен грузиться без компиляции, логика не должна блокировать GUI-поток.

**Решение.** UI — QML с диска. Логика — JavaScript в QML для лёгкого и отдельный процесс с JSON-RPC по stdio для тяжёлого. Нативные C++-плагины только встроенные.

**Альтернативы.**

| Вариант | Почему отказ |
|---|---|
| нативные C++-плагины через `QPluginLoader` для всех | привязаны к версии Qt и компилятору; стороннему автору пришлось бы собирать под каждую сборку roost |
| WASM-модули (как у Zed) | своего UI у них нет, пришлось бы изобретать протокол описания панелей |
| Lua (как sheprd) | второй скриптовый язык рядом с QML JavaScript без выигрыша |

**Последствия.** Два места исполнения кода плагина. Бэкенд-процесс стоит памяти, поэтому он необязателен.

### ADR 011: два стиля нейминга, граница — `src/qml_api/`

**Контекст.** Нейминг взят из zet: функции и методы — PascalCase. QML требует, чтобы имена свойств начинались со строчной буквы, а идентификатор с заглавной разбирает как тип или прикреплённое свойство; сигналы и методы в QML тоже пишутся camelCase. C++-типы, зарегистрированные в QML, отдают ему свои имена как есть.

**Решение.** Весь C++ — в стиле zet. Типы, которые видит QML (`QML_ELEMENT`, `QML_SINGLETON`, их `Q_PROPERTY`, сигналы, `Q_INVOKABLE`), живут в `src/qml_api/`, и там функции и методы camelCase. QML-файлы — по правилам QML. `readability-identifier-naming` берёт стиль из `.clang-tidy` каталога, где объявлен идентификатор (`GetConfigPerFile`, по умолчанию включён; `clang-tools-extra/clang-tidy/readability/IdentifierNamingCheck.cpp:1476-1499` в llvm-project `7600443571`), поэтому граница проверяется автоматически.

**Альтернативы.**

| Вариант | Почему отказ |
|---|---|
| camelCase во всём C++ | код расходится с zet без нужды: QML видит малую часть C++ |
| граница по пометке (`Q_INVOKABLE`, `signals:`), а не по каталогу | `clang-tidy` не отличает эти макросы от обычных методов, правило было бы непроверяемым |

**Последствия.** `src/qml_api/` — тонкий слой: классы там переводят вызовы QML в C++-ядро и не держат логики. Например, `TerminalItem` только отдаёт `updatePaintNode` рендереру из `src/terminal/`. Вспомогательные методы этих классов тоже camelCase, даже если QML их не видит.
